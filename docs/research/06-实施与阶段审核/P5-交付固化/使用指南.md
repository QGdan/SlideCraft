# PPT 六阶段工作流使用指南

本工作流是 Windows 本地候选版本。已验证 unified-v3 暖白青绿模板、8–20页、原生文字、单系列两类别非负横条图、三列表格和组合流程。AI插画为位图。任意品牌模板、复杂图表、Figma到PPTX可编辑往返仍未验证；质量报告含 unknown 时只能交候选稿。

## 直接开始

在 Codex 中输入 `$ppt-quality-workflow`，说明主题、受众、演讲时长、页数、现有资料、品牌要求与编辑要求。总控读取当前阶段，分别调用以下 Skill：

| 命令 | Skill | 你审核什么 |
|---|---|---|
| intake | `$ppt-intake` | 需求、缺失信息、任务边界 |
| outline | `$ppt-outline` | 资料来源、事实口径、逐页主张 |
| template | `$ppt-template` | 整套模板、字体配色、代表样页 |
| compose | `$ppt-compose` | 按批准模板制作的实际PPT |
| polish | `$ppt-polish` | 留白、图形、对齐与非事实措辞 |
| review | `$ppt-review` | 内容、原生对象、逐页视觉与未验证项 |

每个 Skill 可以单独使用。例如“使用 `$ppt-polish`，美化这份PPT，保持数据与品牌不变”。持久化链路要求有效上游交接与用户批准；单独调用不会伪造这些审批。终端阶段命令只返回路由和验证文件，不能自行执行语言模型 Skill。

## 安装与运行条件

一期实测环境为 Windows x64、Python3.12.4、Node24.11.1和本机正版 PowerPoint16。Node直接依赖固定PptxGenJS4.0.1，独立MCP环境固定mcp2.3.0、pywin32 312；更多版本见锁文件。需要本机微软雅黑。包内不附Office、Python、Node或商业字体；WPS尚未做等效验证。

解压候选包到新目录后，在其中的 `ppt-workflow` 运行。所有示例中的 Node 路径应换成本机真实路径：

```powershell
python -X utf8 scripts/bootstrap.py --node D:/node/node.exe
python -X utf8 scripts/bootstrap.py --node D:/node/node.exe --apply
.\.venv\Scripts\python.exe -m ppt_workflow doctor
```

第一条预览，第二条从包内经过哈希校验的离线依赖创建 `.venv`、`.mcp-venv` 和 `node_modules`。它不覆盖已有环境，不运行npm安装脚本，不修改全局依赖。定制Node安装可增加 `--npm-cli <npm-cli.js路径>`。支持范围限定Windows x64/Python3.12，其他环境应重新准备锁与wheel，不能直接声称兼容。

安装项目绑定型 Skill：

```powershell
.\.venv\Scripts\python.exe scripts/install_skill.py --dest "$env:USERPROFILE/.codex/skills"
.\.venv\Scripts\python.exe scripts/install_skill.py --dest "$env:USERPROFILE/.codex/skills" --apply
```

默认预览/安装六阶段及一个总控。仅装一个可追加 `--skill ppt-outline`。任一目标已存在就拒绝整次复制，不覆盖已有技能。安装后 `runtime.json` 绑定当前解压目录；保留该目录，移动后需在新位置重新生成安装副本，不能手改旧任务的审核哈希。新技能在后续会话或应用刷新技能列表后识别；安装文件存在不代表当前对话已刷新。安装的是候选工作流能力，不表示正式PPT质量已全部通过。

## 六阶段文件交接

在运行时根目录执行：

```powershell
.\.venv\Scripts\python.exe -m ppt_workflow skills
.\.venv\Scripts\python.exe -m ppt_workflow intake --workspace runs/my-job
.\.venv\Scripts\python.exe -m ppt_workflow intake --workspace runs/my-job --input requirements.json
```

无 `--input` 时返回应加载的 Skill 路径与缺失交接；宿主读取该 Skill 并完成工作，提交实际文件。产物格式见各 Skill 的 SKILL.md；完整批准与返修协议见 `skills/ppt-quality-workflow/references/stage-handoffs.md`。

提交完整产物后停在审核。收到真实用户确认，才用返回的完整 artifact_sha256 登记：

```powershell
.\.venv\Scripts\python.exe -m ppt_workflow intake --workspace runs/my-job --approve <完整artifact_sha256> --reviewer user --evidence "本次用户实际批准依据"
.\.venv\Scripts\python.exe -m ppt_workflow outline --workspace runs/my-job
```

依次使用outline、template、compose、polish、review。上例是语法，不能把示例文字当作批准证据。用户应审核实际需求/大纲/样页/成品，而不是仅批准空计划。每阶段附件、规则和上游哈希会被核对，变化会使相关审核失效。

## 跑通安装演示

这是明确标为示意的功能演示，沿用项目自有模板。生成器为本机路径重新登记图片，不会依赖作者电脑上的历史run：

```powershell
.\.venv\Scripts\python.exe scripts/create_demo.py --node D:/node/node.exe --out examples/my-demo
.\.venv\Scripts\python.exe -m ppt_workflow plan --config examples/my-demo/workflow.json --out runs/my-demo
.\.venv\Scripts\python.exe -m ppt_workflow build --run runs/my-demo --with-qa
```

`runs/my-demo/rev-000/deck.pptx` 是生成的候选稿，`render-000/slides` 是本次PowerPoint图像，`qa-000/qa.json` 是报告。`create_demo` 中 reviewer 为功能探针，不能被用作新业务内容的人审批准。包内旧 `examples/brief.json`、deck.json、qa.json仅是Schema夹具；不把它们当作完整模板样例。

返回码0表示命令完成，1表示失败/被阻止，2表示待审核、需补信息或未验证。`build --with-qa` 返回2可以同时存在渲染成功的PPT，应阅读QA具体原因，不能只看退出码认定坏文件或改成0掩盖限制。

## 内容与模板修改

新需求先回intake；事实、统计口径或标题主张变化回outline；品牌、主题或布局系统变化回template。更新后重新制作及审核，保留旧版本。

底层 `revise --run ... --patch ...` 仅支持真实QA定位的正文框小幅扩大，最多两轮，不能用它任意改写事实。其他已授权内容更改通过更新spec并新建构建任务完成。`build --resume` 仅适用于输入与生成器都未变化的同一任务。

P4的automizer模板填充是隔离实验辅助路线，不在此安装包默认构建链中。当前主路线仍是原生生成后通过自有MCP stdio调用PowerPoint。没有自动注册Codex全局MCP服务，也没有连接WPS。若调用Figma或生图，按宿主当时实际可用的工具执行并留记录，不能假设固定模型ID或将Figma改动视为已同步PPT。

## 如何看质量报告

`failed` 表示已发现问题；`needs_review`表示需要视觉/人工判断；`unverified`表示有检查未覆盖；`passed`仅表示所声明的支持范围通过。零error不等于全面通过。当前完整OOXML schema、表格复杂继承、目标软件的完整字体测量和交互编辑回存仍可能unknown。

视觉审核应查看接触表及全尺寸逐页图，记录标题断行、标签、裁切、对象对齐、跨页风格和数值口径。按底层审核协议绑定本次PPT/spec/自动QA/图像哈希；可用的宿主视觉API调用前先 `qa --reserve-visual-call`，全任务含失败最多三次。宿主直接看图不能自动清除其他unknown。

`deliver`仅接受ready、QA passed及有效视觉记录，未覆盖项或warning仍未解决时会拒绝。它不是“导出候选稿”命令。评审候选可直接打开工作目录PPT；保留其QA报告，不称正式release。

## 失败恢复

| 情况 | 处理 |
|---|---|
| bootstrap发现已有环境 | 使用新的解压目录；不覆盖或删除现有环境 |
| 依赖哈希不一致 | 重新取得完整候选包，不关闭哈希校验 |
| PowerPoint已有会话 | 保存并自行关闭正在编辑的PPT后再运行，worker不会接管 |
| Office超时/清理不确定 | 查看worker报告与隔离锁；先确认进程归属，不全局结束PowerPoint或直接删锁 |
| 输入、图片或生成器改变 | 新建plan与运行目录，原批准不能复用 |
| 环境故障 | 证据核对后显式 `--retry-environment`，全任务最多一次 |
| 内容/视觉仍不合格 | 最多两轮有限修复；之后提交候选与问题记录，等待用户决定 |

完整207项研究回归依赖原项目历史夹具，在原项目运行 `python -m unittest discover -s tests -v`。候选包只带可迁移的77项检查，可执行 `.\.venv\Scripts\python.exe scripts/smoke.py --node D:/node/node.exe`；覆盖合同、基础QA、渲染故障注入、真实图表生成和安装器保护。包内不含完整历史审核run，不能把77项当成全部质量验收。`docs/任务验收矩阵.md`记录六类任务的实际范围。
