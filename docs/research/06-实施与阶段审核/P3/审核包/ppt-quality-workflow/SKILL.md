# 高质量 PPT：统一模板与可审核工作流

先确认视觉系统和内容，再生成整套 PPT。使用本 Skill 相邻 `runtime.json` 定位项目；生产代码只有项目中的一份。旧 `skill/` 是历史输入，不修改它。

## 按实际任务进入

- 已有任务目录：先读 `state.json`，使用 CLI 恢复；不要覆盖旧 revision。
- 新任务：确定受众、页数、核心结论、事实来源和品牌要求；已有信息不重复询问。先做模板或代表样页，用户确认后冻结配色、字体、网格、十类布局和插画风格。
- 需要生成插画或在 Figma 修改：按 [视觉素材与 Figma](references/visual-tools.md) 操作。
- 构建、检查、修订或交付：按 [命令与审核记录](references/cli.md) 操作。

## 已实现的执行边界

运行 `scripts/run.py doctor` 检查环境，或在项目虚拟环境运行 `python -m ppt_workflow`。当前 CLI 使用 unified-v3 的十类版式，可组合为 8–20 页。原生图表限单系列两类别横条对比，表格限三列；其他图表形式应扩展并验证引擎后再用，不能静默改变图表类型。任意品牌模板和 Figma 到 PPTX 的可编辑往返尚未验证，不把现有演示内容当作通用内容生成器。

叙事、内容精简、模板选择和视觉判断由宿主 agent 完成。脚本接受确定的 brief/spec/config，负责生成、来源和数值核对、原生对象检查、Office 渲染、审核绑定及状态转换。不要把主题配置或生成速度当作视觉质量证明。

原生文字、图表、表格和流程优先。AI 插画是局部素材；需要调整其结构时按语义重建为形状、文字或 SVG，并明确这不等于无损拆解原图。保持同一套插画的背景、材质、光线和色彩一致，不拼贴风格无关的整页图片。

## 审核与恢复

每个 revision 保存 PPT、日志、QA、渲染、对象映射和审核请求。输入、事实来源、资产、模板、生成器变化后原审核失效，应重新规划；`--resume` 只适用于哈希完全匹配的任务。

接触表检查整套节奏，再查看每页全尺寸图。按照 `review-request.json` 的 binding 填写逐页观察、跨页一致性和内容判断，保存为独立记录后用 `qa --review` 绑定。评分不能覆盖严重缺陷，未查看的页面不能填写通过。

最多两轮有定位证据的局部修复。CLI 只允许正文框在原位置小幅扩大，不能改数字、事实口径、字体、品牌或共享页眉页脚；这些修改应退回设计与内容审核。环境故障最多一次显式重试。使用视觉 API 前通过 `qa --reserve-visual-call` 预留额度，含初次最多三次，失败也消耗额度；无视觉 API 时使用宿主图像审阅。

`deliver` 拒绝 failed、needs_review、unverified，以及未解决的 warning。人工视觉审阅只确认画面，不能替代未执行的 OOXML 校验或交互编辑验证；不要删除 coverage unknown 来放行。可以提交待审核候选稿，并清楚标注尚未正式交付。

项目采用逐阶段审核；完成当前阶段后提交证据与限制，再等待下一阶段授权。现有 Office 用户会话与隔离锁由 worker 保护，不全局杀进程。最终全局 Skill 安装和新环境验收留在约定的安装阶段。
