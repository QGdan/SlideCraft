# PPT 工作流详细实施计划

版本：1.0；日期：2026-10-13。承接已审核的开源研究方案，本轮开始实施。

## 1. 已确定的实施范围

一期以 Windows 本地和 PptxGenJS 原生生成通路为主，面向中文及中英混排的 8–20 页展示型 PPT。常见数据图表、表格、标题和正文保持可编辑。目标是安装可复现、任务可追溯、失败可识别、结果可审核。

生产代码放到 `ppt-workflow/`，阶段记录放到 `06-实施与阶段审核/`。原来的报告、脚本、Skill、示例和渲染图作为历史基线保留。先建立新实现，再决定是否替换旧 Skill；不同时维护两套手工复制的生产脚本。

新工作流的主链路：brief → 资料与事实表 → outline → design/spec → build → static QA → render → visual/content review → bounded revision → deliver。设计样页与阶段审核均保存可定位的文件。

## 2. 审核方式

每阶段按“实现 → 自动检查 → 产物核对 → 审核包 → 用户审核”执行。用户确认本阶段后才进入下一阶段；不能把自动测试通过代替用户阶段审核。

审核包统一包含：阶段目标、实际变更、可运行命令、测试结果、未完成/未验证项、风险和下一阶段范围。状态记录在 `阶段状态.json`。允许结果为：通过、带条件通过、要求修改；带条件通过时记录限制，不隐式扩大授权。

同阶段内的依赖安装、局部修复、测试重跑和文档修订持续进行，无需逐次确认。遇到阶段目标改变、付费外部服务或真实业务材料缺失时，先完成不依赖这些条件的工作，并明确需要的输入。

```mermaid
flowchart LR
  P0[ P0 环境与接口基线 ] --> G0{用户审核}
  G0 --> P1[ P1 验收基础 ]
  P1 --> G1{用户审核}
  G1 --> P2[ P2 内容与设计组件 ]
  P2 --> G2{用户审核}
  G2 --> P3[ P3 编排与 Skill ]
  P3 --> G3{用户审核}
  G3 --> P4[ P4 模板与对照试点 ]
  P4 --> G4{用户审核}
  G4 --> P5[ P5 安装与交付固化 ]
  P5 --> G5{最终审核}
```

## 3. P0：环境、依赖、接口和基线

### 实施顺序

1. 记录 Python/Node/Office 注册和运行情况，检查缺失依赖。
2. 创建项目内 Python venv 与 Node package，固定 PptxGenJS 4.0.1 及 Python 依赖；生成实际安装 lock/report。安装不修改全局依赖。
3. 保存原报告、工具、示例、校准资产的 SHA256 清单及代码快照。
4. 复制原示例生成器到独立 run 目录，重新生成 PPTX；对原件和重建件运行旧 linter/结构检查，记录实际输出。基线失败也必须保留，不能改数据或阈值让它通过。
5. 对重建 PPTX 尝试 PowerPoint 1600×900 导出；记录退出码、输出页数/尺寸/hash。已有用户 PowerPoint 会话时不采用会退出共享应用的旧脚本。
6. 实现 brief、deck、QA 三个 JSON Schema 和对应正/负例；明确 ID、单位、对象编辑性、未验证状态和 issue 定位合同。
7. 交付 P0 审核报告及环境清单，停在 G0。

### 产物与通过条件

| 产物 | 验收要求 |
|---|---|
| package.json / package-lock.json | 固定直接依赖，记录实际传递依赖和 integrity |
| requirements.lock.txt / pip-install-report.json | 精确 Python 安装版本，保留下载/安装溯源 |
| baseline-manifest.json | 原文件 hashes、生成源和运行环境可追溯 |
| baseline-run.json / logs / rebuild deck | 确认生成是否成功，旧检查结果原样保存 |
| rendered PNG / render-manifest.json | 成功则 10 页、1600×900；失败则明确未渲染，不假成功 |
| schemas + examples + contract tests | 正例通过，负例被拒；未知 QA 不可宣称 pass |
| P0 阶段审核.md | 总结实际证据、限制及 P1 范围 |

P0 不修复旧 QA，也不重新设计示例。旧示例的字号/留白和业务口径问题登记到 P1/P2。COM 无法运行时继续完成其余 P0 事项，G0 明确列为“带限制”，不伪装整阶段完全通过。

## 4. P1：验收基础与可复现缺陷

### 任务分解

| 工作包 | 具体实现 | 有意义的验证 |
|---|---|---|
| P1.1 包结构 | 用安全 XML 解析替代正则；校验内部 relationship、media、图表 axId/crossAx、内容类型 | 坏引用被检出；合法单轴/双轴不误报 |
| P1.2 所有对象边界 | 递归组对象，组合变换/缩放，非文字对象与表格纳入 | 画布外矩形、组内文字、缩放组负例；允许裁切背景有明确豁免 |
| P1.3 文字与字体 | 处理背景继承、主题色、段前/段后、点值行距；style-aware font resolution；返回缺字形状态 | 正负例逐类验证；长词标风险，不伪称已模拟 PowerPoint 断行 |
| P1.4 可读性 | 按角色字号、粗体大字对比度；未知背景/字形返回 unverified | 主题/透明/图片背景分清可算与不可算 |
| P1.5 渲染可靠性 | 独立 revision 目录，timeout、退出码、页数/尺寸/hash；COM 归属检查；LO 可选 | 缺 pdftoppm、转换非零、缺页和旧图都不返回成功 |
| P1.6 统一 QA | 输出统一 qa.schema；hard failures 优先；coverage/unknown 单列 | 不能用零 issue 掩盖跳过的规则 |

建立至少 24 类微型用例，包含正确/错误对照。保留本轮五个探针，升级为断言缺陷必须被发现的测试。检测不到的特殊对象先报告未覆盖，不用过于乐观的通用 fallback。

审核包：QA v2、测试清单/输出、原探针前后结果、渲染失败演练、已支持/未支持矩阵。G1 重点审核覆盖声明是否可信，原示例回归是否解释清楚。

## 5. P2：内容、主题与可编辑组件

1. 实现来源/事实表：source ID、原文定位、数值、单位、口径、时间、示例标志、公式；检测跨页复用时的冲突。
2. 将旧示例统一为明确标注的示意数据；40分钟→1分钟的例子使用同一事实 ID，不保留无解释的0.9秒口径。
3. 实现三套主题：学术、商务、技术。展示型初始字号：标题28–40、正文18–24、图表标签≥14、来源≥10；主题覆盖用户品牌要求。
4. 实现十类布局：封面、结论、KPI、对比、图表+结论、流程、时间线、表格、章节、结尾请求。
5. 从 spec 的自有坐标与组关系计算版式，不靠修改 PptxGenJS 私有对象；允许复杂素材作为登记的局部图片。
6. 普通常见图表用 native charts，并验证内嵌数据；表格保留单元格。每个输出对象与 element ID 有映射。
7. 每套主题给出样页与一个中文整套示例，渲染、静态 QA 和画面检查均执行。

审核包：三套主题接触表、代表页全尺寸图、可编辑 PPTX、spec、来源表、QA 和限制。G2 审核视觉风格、阅读尺度、内容精简程度；若不满意，在本阶段修正主题和组件。

## 6. P3：编排、有限修复与 Skill

实施命令：doctor / plan / build / qa / revise / deliver / benchmark。CLI 接收确定的文件输入，避免要求每次填写零散参数。

核心实现：

- 明确状态转换；failed、needs_review、unverified 是真实状态，deliver 不接收它们。
- 输入/spec/source/theme/engine hash 绑定审核；任何影响内容或外观的修改使原审核失效。
- 每个 revision 保存 PPTX、logs、QA、render、review 和 manifest；断点续跑须匹配输入 hash。
- 初次构建后最多两轮内容修复；环境故障最多一次重试；视觉 API 调用最多三次含初次，失败不当通过。
- 确定性局部修复只改有定位证据的对象；改数据、事实口径和品牌元素必须退回审核。
- agent 承担叙事和视觉判读，脚本承担可重复检查；无视觉 API 时允许宿主图像审阅并保存 review record，不能省略它。
- 接触表用于跨页节奏，全尺寸图/裁剪用于细节；整体评分不覆盖严重问题。
- 编写新的自有 Skill 和安装入口；Skill 只声明代码真实支持的功能。

审核包：一条命令执行演示、失败演示、修改使审核失效的演示、完整交付包、Skill 原文。G3 审核实际操作是否清晰，是否能维护和重跑。

## 7. P4：模板与开源对照

### 模板通路

先用现有合法自有示例作受限模板试验，再在用户提供真实学院/品牌模板后验证。若未收到真实模板，仅标记“合成/自有模板通过”，不能称真实学院模板已通过。

pptx-automizer 独立固定版本，先消除 package/CHANGELOG 版本差异。验证母版、布局、图表工作簿、超链接、notes、图片与组关系。动画与不支持对象单独列出，必要时保留原页或交人工处理。

### 对照通路

三个通路各一套初筛；通过安装、许可、原生编辑性门后，两个入选通路在两套共同任务上各跑三次。PPTAgent 的平台条件在开始安装前核查；无法满足则记录 unsupported。Slidev 的逐对象/逐页图片回退必须计入编辑性结果。PPT Master 保留备选；Presenton 先完成 export-core 来源和许可核验。

数据同源、页数同约束、字号同尺度；记录生成/渲染/评审耗时、调用费用（可获得时）、修改次数和人工修改时间。不能凭生成速度或截图美观就替换主引擎。

审核包：同材料对照图、编辑性清单、实测表、模板样例、候选留用/放弃理由。G4 决定最终通路，不预设赢家。

## 8. P5：安装、示例和最终交付

1. 收敛依赖与代码来源记录；脚本单一来源；生成可安装自有 Skill。
2. 完成六类主线任务验收；校准集与留出集区分，记录未支持任务。
3. 在新环境按 lockfile 安装并跑 smoke/e2e；从生成源可重建。
4. 写快速开始、依赖/字体条件、CLI 用法、质量报告解释、修订与失败恢复教程。
5. 最终交付：源码、锁文件、Skill、完整示例、PNG/接触表、sources/editability/manifest/QA、已知限制。

G5 审核安装可复现性、典型成品和限制，确认后才发布为正式可用版本。个人全局 Skill 安装在最终阶段执行，不在 P0 修改用户已有配置。

## 9. 回退与变更管理

无 Git 仓库，P0 先用 SHA256 和快照保护历史基线；后续代码修改保存阶段快照，不为此擅自初始化或改动其他仓库。任何阶段失败只影响新增目录，原始交付包可继续使用。

阶段测试以实际需求和失败模式为依据；低影响的文档修改不单独增加形式化测试。生产依赖安装限定项目目录，外部候选不一次全量部署。未经用户审核不进入下一阶段，未测得指标不写成成功结论。
