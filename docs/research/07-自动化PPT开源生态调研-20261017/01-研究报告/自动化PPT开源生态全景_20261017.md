# 自动化高质量 PPT：开源生态、插件与工作流全景

**研究日期**：2026-10-17（北京时间）  
**范围**：30 个代表性项目/插件（含 3 个评估基准）+ 4 类插件形态 + 6 种工作流模式  
**性质**：公开资料、源码与官方文档核查；**未在本机安装或运行任何新候选项目**，不构成实测质量排名  
**与既有研究的关系**：`../../05-开源项目深度研究/` 下 2026-10-13 的 `generation-research.md`、`skills-research.md`、`qa-research.md` 已完成“候选选型 + 本地探针”；本报告不重复那三份的源码级审计，而是补齐**全景地图、插件层、工作流模式与接入映射**，并更新 2026 年 9–10 月的新变化。

> **证据口径**：星数为 2026-10-17 通过 shields.io 抓取的快照，只用于判断社区规模，**不作为质量或稳定性排名**。项目能力以 README/官方文档/源码入口为准；凡未本地运行的能力，一律写“自述/文档支持”，不写“实测通过”。许可证以仓库根目录与文件级声明为准；素材、字体、模板、模型权重、外部导出包需另行核查。

## 0. 一页结论

1. **生态已经分化为五条路线**：原生库编程、标记语言编译、HTML/SVG 设计源、模板复用、Agent 端到端。它们不是替代关系，而是“质量/成本/可编辑性”三角上的不同取舍。
2. **2026 年的分水岭是“可编辑 PPTX”从实验走向基线**：Slidev 增加 `pptx-editable`，Marp 提供实验性 `--pptx-editable`，PPT Master 用“受约束 SVG → DrawingML”，PPTAgent 转向“HTML → PPTX + 双重视觉评审”。
3. **质量瓶颈不在“生成”，而在“布局决策 + 验收闭环”**。模型能写出像样的句子，却很难稳定判断“这页会不会溢出、这组对比是否成立、观众第一眼看到什么”。
4. **模板仍是最稳的质量杠杆**。对品牌汇报，模板注入（版式/占位符/母版继承）在质量、成本、可编辑性三方面同时优于“自由生成”。
5. **自由设计要成立，必须配约束中间表示**：JSON deck spec 或受约束 SVG，加上几何/字体/对比度检查器；否则每页都是不可复现的即兴创作。
6. **Agent 的护城河是视觉回环与失败恢复**，不是文案生成。PPTAgent 的 `review-slides → build → review-deck → finalize`、PPT Master 的 early/final quality gate，都比“一次生成”更值得借鉴。
7. **插件层已成型，但价值是“把确定性工具暴露给概率模型”**：MCP、Agent Skill、Dify/n8n 节点、Office 加载项。工具越多不等于质量越高，正确的抽象是少数稳定原语：`measure / render / lint / export`。
8. **评估正在从“看截图打总分”转向“二元清单 + 硬门禁 + 确定性扣分”**：PPTEval 三维、SlidesBench、PresentBench（238 例、每例平均 54.1 项二元清单）、PPTBench（科学图重建硬门禁）。
9. **对本项目的建议是“零件化接入，不平台化替换”**：PptxGenJS 主引擎与六阶段工作流不变；把 PPT Master 的 SVG 编译、PPTAgent 的双评审、Presenton 的模板/API、Slidev 的 DOM 测量分别作为能力供应商接入。
10. **先做基准集，再谈选型**。没有 20 页中文固定测试集与 E0–E4 可编辑性口径，任何“哪个项目更好”的结论都不可复现。

## 2. 先把“高质量”拆开：五层乘法模型

“高质量”常被混成一个总分。工程上必须拆成五层，否则无法定位失败原因：

| 层级 | 定义 | 典型失败 | 现有工具能否自动发现 |
|---|---|---|---|
| **L1 内容正确** | 事实、数字、引用、来源可追溯 | 编造数据、张冠李戴、过期结论 | 难；需来源表与人工/检索核对 |
| **L2 叙事结构** | 每页一个结论、页间有论证关系、行动标题 | 标题是名词标签、页与页并列无递进 | 部分；可用“幽灵 deck 测试” |
| **L3 视觉设计** | 网格、层级、对比、留白、字体、配色、图表选型 | 内容吊在顶部、字号过小、颜色过多 | 部分；对比度/字号可算，审美需人 |
| **L4 工程可交付** | 原生可编辑、字体、无溢出、文件有效、跨端 | 文本溢出、字体回退、PPT 打开修复 | 较多；linter/结构检查/渲染 |
| **L5 生产可运维** | 模板治理、批量、幂等、审计、成本 | 每次样式漂移、无法复现、版本失控 | 需自建流水线 |

**关键判断：质量是乘法，不是加法。**

```
Q = L1 × L2 × L3 × L4 × L5
```

任一层为 0，整体为 0。一个“lint 0 error”的 deck 可能 L1 全错；一个视觉惊艳的 deck 可能整页是图片、L4 为 0。反过来，L4 做得好不能弥补 L2 的空洞。这解释了为什么“生成工具越来越多，但高质量 PPT 仍然稀缺”。

**对自动化的含义**：不要把预算全押在“生成”上。一个可用的系统至少要有：

1. 结构化内容层（每页结论 + 证据 ID）；
2. 受约束的版式层（页型组件/模板槽位）；
3. 确定性渲染层（目标渲染器）；
4. 可定位缺陷的验收层（几何 + 视觉 + 内容）；
5. 失败恢复层（回退、重跑、人工接管）。

## 3. 技术版图：五条路线

| 路线 | 核心抽象 | 代表项目 | 可编辑上限 | 设计上限 | 单页边际成本 | 典型失败 |
|---|---|---|---|---|---|---|
| **A 原生库编程** | 代码/JSON → OOXML 对象 | PptxGenJS、python-pptx、Open XML SDK | **E4** | 中（取决于你的组件库） | 低 | 坐标硬编码、溢出、字体回退 |
| **B 标记语言编译** | Markdown → 主题化页面 | Marp、Slidev、Quarto/Pandoc、Typst/Touying | E0–E4 | 中高（CSS/主题） | 极低 | 版式同质化、复杂图表弱 |
| **C HTML/SVG 设计源** | 设计系统 → 页面 → 测量/编译 | reveal.js、Slidev、PPT Master、visual-explainer | E2–E4 | **高** | 高 | 浏览器与 PowerPoint 度量差异 |
| **D 模板复用** | 既有 PPTX → 复制/填充 | pptx-automizer、python-pptx、PPTist、Presenton | **E4** | 高（受模板上限约束） | 低中 | 版式不匹配、关系部件丢失 |
| **E Agent 端到端** | 资料 → 计划 → 页面 → 评审 → 修复 | PPTAgent、PPT Master、Presenton、AutoPresent、Paper2Slides | E0–E4 | 高但不稳 | 高（token/重试） | 不可复现、视觉回退、幻觉 |

### 3.1 路线之间的真实关系

- **A 是底座**：B/C/D/E 最终都要落到 OOXML 对象或图片。A 的能力边界（能否原生图表、能否继承母版）决定上层天花板。
- **B 是效率**：用 Markdown/CSS 换取“内容与版式分离”，适合技术分享、课程、快速迭代；代价是设计自由度与复杂图表。
- **C 是质量**：用浏览器/SVG 的布局能力换设计上限；代价是“浏览器度量 ≠ PowerPoint 度量”，必须重建与复检。
- **D 是品牌**：用既有模板换一致性；代价是模板覆盖率与关系部件复制。
- **E 是自动化**：用模型换人力；代价是稳定性、成本与可审计性。

**结论**：不存在“一条路线通吃”。成熟系统通常是 **D（模板）+ A（原生对象）+ C（设计源）+ E（编排）** 的组合，B 作为快速通道。

## 4. 重点项目深评

### 4.1 原生生成库

#### PptxGenJS（MIT，约 6.3k stars）

- **定位**：JavaScript/TypeScript 生成原生 PPTX 的主力库，Node/浏览器/Electron 均可运行。
- **能力**：文本、形状、表格、图片、图表、SVG、母版/版式；75+ 示例；输出 OOXML，PowerPoint/Keynote/LibreOffice/Google Slides 可打开。
- **边界**：不提供“加载任意既有 PPTX 并编辑”的通用 API；布局、留白、中文字宽、表格分页都要自己算。README 的“zero runtime dependencies”与包清单不一致，引用时不要照抄。
- **适用**：新建原生可编辑页面；与自研组件库/设计 token 配合。
- **风险**：几何全靠代码，必须有 linter + 渲染验收；复杂图表仍需检查 PowerPoint 打开后的轴/标签。

#### python-pptx（MIT，约 3.6k stars）

- **定位**：Python 侧读写 PPTX 的标准库，最适合“打开既有模板 → 填占位符 → 后处理”。
- **能力**：读取既有 presentation，继承 master/layout；原生文本、表格、图表；可做 XML 级检查。
- **边界**：不是渲染引擎；SmartArt/动画/复杂组合的编辑能力有限；跨文件复制复杂对象容易丢关系。
- **适用**：模板注入、批量替换、结构检查、生成后处理。
- **风险**：模板版式索引不保证稳定；不要把它当“万能 OOXML 编辑器”。

#### pptx-automizer（MIT，约 250 stars）

- **定位**：Node 模板库，从既有 PPTX 复制 slide/master/layout，并填充文本、图表、表格；可调用 PptxGenJS 追加动态对象。
- **能力**：关系部件复制（chart/image/diagram/OLE/hyperlink/notes）有明确代码路径。
- **边界**：动画不在支持范围；依赖 PptxGenJS 3.x，与主线 4.x 的 API 不完全一致；复杂模板仍需逐份验收。
- **适用**：企业品牌模板通道的首选 POC；比“从零画模板”更接近真实交付。
- **风险**：复制不是无损承诺；母版/版式/图表工作簿要在真实 PowerPoint 中回归。

#### Open XML SDK / pptx-renderer

- **Open XML SDK**（MIT，约 4.6k）：.NET 的 OOXML 强类型操作与 `OpenXmlValidator`，适合做“文件结构是否合法”的硬门禁；不能判断视觉质量。
- **pptx-renderer**：浏览器端 OOXML → HTML/SVG 的高保真渲染器，适合做预览与像素回归；不是生成器。证据等级 C，需自测覆盖范围。

### 4.2 标记语言与网页幻灯片

#### Marp（MIT，CLI 约 3.9k）

- **定位**：Markdown + CSS 主题 → HTML/PDF/PPTX/图片，确定性最强、上手最快。
- **关键边界**：默认 `--pptx` 是**整页图片**；`--pptx-editable` 是实验特性，依赖浏览器 + LibreOffice，复杂主题可能失败或不完整，且不支持演讲者备注。
- **适用**：10 页内的技术分享、课程材料、PDF 出版；作为低成本基线。
- **不要**：把 Marp 的 editable 输出当作复杂品牌 deck 的主线。

#### Slidev（MIT，约 49k）

- **定位**：Markdown + Vue 的开发者幻灯片，交互、代码高亮、组件生态强。
- **关键边界**：`--format pptx` 仍是整页图片；`--format pptx-editable` 在浏览器测量 DOM 后重建文本框/形状，但 SVG、canvas、iframe、视频、KaTeX、渐变、filter、clip-path 等按元素图片化；无法安全重建的页会整页回退并打印原因；字体不嵌入，长段落换行可能变。
- **适用**：技术演讲/网页优先；需要交 PPTX 时，把 editable 作为 E3 对照，逐页记录回退。
- **价值**：它的“DOM 测量 → 原生对象重建”是目前最接近“网页设计自由度 + PowerPoint 可编辑”的公开实现之一。

#### reveal.js / Quarto / Typst-Touying

- **reveal.js**（MIT，约 72k）：HTML 演示框架的事实标准；PDF 靠打印，PPTX 不是原生目标。适合网页优先、需要嵌入交互的场景。
- **Quarto/Pandoc**：Pandoc 的 `--reference-doc` 是“模板驱动”的经典实现，Quarto 在其上做科学生态；确定性好、设计上限取决于 reference doc。
- **Typst/Touying**（约 2.4k）：排版质量高、编译快，但输出 PDF，不解决 PPTX 可编辑；适合学术/印刷型材料。

### 4.3 Agent 与端到端

#### PPTAgent / DeepPresenter（MIT，约 5.1k）

- **定位**：ICIP（中科院软件所等）的“反思式 PPT 生成”研究框架，已从论文代码演进为 coding-agent skill。
- **论文贡献**：两阶段“参考演示分析 + 编辑动作生成”；提出 **PPTEval**（Content / Design / Coherence 三维）。EMNLP 2025。
- **后续演进**：DeepPresenter（ACL 2026）把深度研究、素材生成与 20+ 工具放进带沙箱的 agent 环境，方向从“一次生成”转向“环境中的反思式执行”。
- **当前形态**：`skills/pptagent` 面向 Claude Code / Codex / OpenCode；流程是“宿主 agent 写 HTML → 渲染 → 视觉评审 → 导出可编辑 PPTX → 复审 deck → finalize”；要求 Linux/WSL/macOS、LibreOffice、Playwright、npm。
- **关键洞见**：任务合同明确“HTML 里的文本度量在转成 PPTX 后会变”，所以**源与导出必须分别审**；修改后旧评审失效。这比“生成完看一眼”成熟得多。
- **边界**：安装重、平台受限；视觉评审依赖多模态模型；论文分数不能当本地质量保证。
- **对我们的用法**：借“双评审 + 评审产物失效”机制，不照搬安装方式与模型绑定。

#### PPT Master（MIT，约 63k）

- **定位**：coding-agent 工作流 + **受约束 SVG → DrawingML** 编译器；目标是“原生可编辑的 PowerPoint 草稿”，不是整页贴图。
- **架构**：资料 → 策略/设计规格 → Executor 逐页写 SVG → `svg_quality_checker.py`（early/final 两道门）→ `svg_to_pptx.py` 编译为原生形状/文本；可选原生图表/表格变体；支持 `edit-native-pptx` 往返、模板蒸馏、图片转 PPTX。
- **强项**：把“设计自由度”与“原生可编辑”同时往前推了一步；质量门有明确的 error/warning 分级与“无自动修复”原则（避免机械补丁覆盖设计意图）。
- **边界**：SVG 是项目私有子集，不是任意 SVG；复杂路径/公式/图表仍需实测；主要由单人维护；可选 PDF 转换依赖 PyMuPDF（AGPL-3.0），根仓 MIT 不覆盖它。
- **对我们的用法**：SVG→原生对象的 POC；把“质量门 + 编译前校验”作为 review 阶段的参考。

#### Presenton（主仓 Apache-2.0，约 11k）

- **定位**：可自托管的 AI 演示生成平台（Gamma 替代），Web/Electron/Docker，BYOK，支持 Ollama/LM Studio/OpenAI/Gemini/Claude 等。
- **能力**：HTML + Tailwind 自定义模板；从 prompt/文档/既有 PPTX 设计生成；PPTX/PDF 导出；内置 REST API 与 **MCP Server**（`/mcp`）；多用户/工作区；模板市场。
- **关键边界**：`slides_markdown` 仍由 LLM 选版式与字段映射，不是确定性 Markdown 渲染；长文本会截断（默认每页 100 词、最多 50 页）。更重要的：导出核心通过独立 release 包 `@presenton/export-core` 固定版本下载，**该包的许可证与完整源码仍需单独核验**；主仓 Apache-2.0 不能自动覆盖它。
- **对我们的用法**：平台化/API 的对照试点；先完成 export-core 溯源，再决定是否接入。

#### PPTist（AGPL-3.0，约 9.4k）

- **定位**：Vue3 + TypeScript 的在线 PPT 编辑器，还原大部分 Office 常用编辑能力；支持导入 PPTX（约 85% 保真）、导出 PPTX（约 95% 保真）、AIPPT 模板生成、`AI_PPT_SCHEMA` 数据结构。
- **价值**：如果需要一个“可编辑的 Web 编辑器底座”，它是最完整的开源选择之一；它的 JSON schema 也适合作为“AI 直接生成页面数据”的中间表示参考。
- **边界**：AGPL-3.0，闭源商用需商业授权；作者明确说“不是开箱即用工具”，需要自建后端；导入/导出不可能 100% 还原动画、复杂图表、母版。
- **对我们的用法**：编辑器/JSON IR 参考；许可证不允许时不要嵌入产品。

#### AutoPresent / SlideCoder / Paper2Slides（研究线）

- **AutoPresent**（CVPR 2025，约 181 stars）：提出 **SlidesBench**（7k 训练 / 585 测试，来自 310 个 deck、10 个领域）；结论是**程序生成**比端到端图像生成质量更高、更可交互；8B Llama 微调后可接近 GPT-4o；迭代自我精修有增益。适合借“程序生成 + benchmark”的方法，不适合直接当产品。
- **SlideCoder**（EMNLP 2025，约 48 stars）：从设计图做 layout-aware RAG + 分层代码生成，最终执行代码产出 PPTX；是“设计→代码→PPTX”路线的代表。工程化程度低，适合研究参考。
- **Paper2Slides**（MIT，约 3.8k）：RAG 四阶段（解析 → 摘要 → 规划 → 图像生成），输出 PNG + PDF；**不是可编辑 PPTX**。适合“论文→视觉草稿/海报”，不适合交付可改的汇报稿。

#### SlideDeck AI / Presentation AI（轻应用）

- **SlideDeck AI**（MIT，约 376）：LLM 生成结构化 JSON → `python-pptx` + 预定义模板 → PPTX；支持 PDF 输入、多模型、Ollama 离线。是“JSON schema + 模板”的最小可用参考。
- **Presentation AI**（MIT，约 3k）：Next.js + 38 主题 + 大纲先行 + 实时生成 + 分享/录制；但 roadmap 明确 PPTX 导出“部分完成，图片和组件不能 1:1 转换”。适合产品 UX 参考，不适合作为引擎。

### 4.4 技能与轻应用

- **visual-explainer**（MIT，约 10k）：把复杂信息渲染成自包含 HTML 页面/幻灯片；提供 `--pptx` 的“best-effort 静态导出”（标题、文本、项目符号、简单表格、代码块；不保留动画/Mermaid/图表）。价值在**版式规则与信息设计**，不在 PPTX 保真。
- **frontend-slides**（MIT，约 31k）：先生成 3 个真实封面预览，再锁定设计系统；固定 1920×1080 舞台；PDF 出口是逐页截图。适合“风格发现”，不是原生 PPTX 引擎。
- **academic-pptx-skill**（MIT）：学术场景的内容规范——行动标题（完整句子）、幽灵 deck 测试、每页一个 exhibit、图内标注、引用规范、结论页而非“谢谢”。这些规则可以直接移植到 outline/review 阶段，与生成引擎无关。

### 4.5 评估基准

| 基准 | 核心方法 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| **PPTEval**（PPTAgent, EMNLP 2025） | Content / Design / Coherence 三维 | 内容、视觉、跨页连贯的相对好坏 | 事实正确性、可编辑性、字号合规 |
| **SlidesBench**（AutoPresent, CVPR 2025） | 7k/585 例；reference-based + reference-free | 程序生成 vs 图像生成；设计质量 | 中文业务场景、模板保真 |
| **PresentBench**（2026-03） | 238 例，每例平均 54.1 项二元清单；带背景资料 | 细粒度、可验证的任务完成度；与人类偏好一致性更强 | 以 slides.pdf 为输入，不能证明 PPTX 可编辑 |
| **PPTBench**（Einsia, 2026） | 500 个科学图单页重建；硬门禁 + 确定性扣分；LibreOffice 25.8 | 原生对象重建、结构/文字/局部图形缺陷 | 整套叙事、商业汇报 |
| **PPTBench-Eval**（Gastronomicluna） | 检测/理解/修改/生成四类任务 | 版式理解与空间操作 | 与上一项同名，不可混算 |

**方法启示**：把“总分”拆成“二元清单 + 硬门禁 + 缺陷定位”，并让机器只负责可验证项，人负责审美与事实。评估输入如果是 PDF，就必须单独声明“未验证可编辑性”。

## 5. 插件生态：四种形态

“插件”在 2026 年已经不是一个东西。至少要区分四层：

| 形态 | 载体/协议 | 代表 | 能做什么 | 不能做什么 | 适合谁 |
|---|---|---|---|---|---|
| **MCP Server** | Model Context Protocol（stdio/HTTP） | Office-PowerPoint-MCP（34 工具）、Presenton `/mcp`、Marp MCP、2slides、Google Slides MCP | 把创建/编辑/导出/渲染暴露给任意 MCP 客户端 | 不保证设计质量；工具过多会增加误用与上下文成本 | 想让 Claude/Cursor/Codex 直接操作 PPT 的人 |
| **Agent Skill** | `SKILL.md` + 脚本 + 资源 | PPTAgent Skill、PPT Master、visual-explainer、academic-pptx-skill、frontend-slides | 把“流程、规则、检查、模板”打包成可复用能力 | 依赖宿主 agent 的文件/命令权限；跨平台差异大 | 已有 coding agent、想固化方法论的人 |
| **工作流节点** | Dify Plugin / n8n node / Coze 插件 | PPT-Dify-Plugin（Markdown→PPTX）、n8n-nodes-presenton | 把生成接入低代码编排、批量、通知、存储 | 节点通常只覆盖“生成”，不覆盖验收 | 运营/自动化团队 |
| **Office 加载项** | Office.js / COM / VSTO / WPS 加载项 | PowerPoint COM（本项目渲染在用）、WPS 加载项、Office Add-in | 在真实 Office 内操作对象、渲染、导出 | 平台绑定、权限/进程管理复杂、难以跨端 | 必须“在 PowerPoint 里”操作的场景 |

### 5.1 MCP：工具不是越多越好

Office-PowerPoint-MCP-Server 提供 32–34 个工具、11 个模块、25+ 内置版式模板，能力覆盖创建、文本、图片、表格、图表、母版、转场、文本提取。它证明了“python-pptx 可以被封装成 agent 工具”，但也暴露了一个设计问题：

> **当工具有 30+ 个时，模型的选择成本、参数错误率和上下文占用都会上升；真正需要的往往是 4 个稳定原语。**

建议的 MCP 原语（而不是 30 个细碎工具）：

1. `measure(spec)`：给定文本/字体/框宽，返回行数、高度、溢出风险；
2. `render(pptx)`：调用目标渲染器输出逐页 PNG/PDF，返回页数与哈希；
3. `lint(pptx)`：几何、对比度、字体、占位符、结构检查，输出可定位缺陷；
4. `export(spec)`：把结构化 spec 编译为 PPTX（模板或原生对象）。

其余能力（加图表、改母版、加动画）应作为 `export` 的参数或独立少量工具，而不是平铺。

### 5.2 Skill：把“方法论”产品化

PPTAgent Skill 与 PPT Master 是两种不同范式：

- **PPTAgent Skill**：宿主 agent 负责研究与写 HTML；Skill 提供渲染、视觉评审、导出、交付校验。核心资产是**流程与评审合同**。
- **PPT Master**：宿主 agent 负责设计决策与写 SVG；Skill 提供约束、检查器、编译器。核心资产是**中间语言与质量门**。

两者都说明：Skill 的竞争力不在提示词长度，而在**可执行的检查与可复现的产物**。

### 5.3 Dify / n8n：把生成变成“工序”

- **PPT-Dify-Plugin**（MIT）：把 Markdown 转 PPTX，支持自定义模板（模板放在 Dify 插件目录），适合“LLM 产出 Markdown → 插件出片”的轻流程。
- **n8n Presenton 节点**：把 Presenton 的生成 API 接进 n8n，适合“表单/CRM/数据库触发 → 生成 → 存云盘 → 通知”的运营流水线。

这类节点的共同短板是：**只覆盖生成，不覆盖验收**。如果直接对外交付，必须外挂渲染与人工审核。

### 5.4 Office 加载项 / COM / WPS

- **COM** 是 Windows 上最可靠的“目标渲染器”，本项目已用于 `render_windows.ps1`；它也是“在真实 PowerPoint 中执行排版边界测量”的唯一途径（`TextRange.BoundHeight/BoundWidth`）。
- **Office.js Add-in** 适合做“在 PowerPoint 内的一键美化/检查”产品，但受沙盒与 API 限制，复杂 OOXML 操作不如 COM/Open XML SDK。
- **WPS 加载项** 在国内环境是现实选择；本项目已验证模板副本编辑、保存、导图与回读，但能力矩阵仍是局部的，不能等同于 PowerPoint 全量兼容。

### 5.5 商业插件的位置

国内商业插件（iSlide、口袋动画、OneKey Tools 等）以人工交互与模板库为主，未见公开 API/开源许可，**不纳入自动化链路**；它们的价值是交互设计、模板审美与批量操作的产品参考，而不是可编程组件。

## 6. 六种可落地工作流

以下不是“工具清单”，而是“输入 → 中间表示 → 渲染 → 验收”的完整工序。每种都给出适用/不适用与质量门。文中的“人日/页”为经验估计，随模板复杂度、资料质量与团队熟练度变化，不构成报价。

### W1 Markdown 极速线（Marp / Slidev）

```
Brief ──> LLM 大纲 ──> Markdown + 主题 CSS ──> Marp/Slidev ──> PDF / PNG / PPTX(图片)
                                                   │
                                                   └─> 人工过目（10 页内）
```

- **适用**：技术分享、课程、内部同步、10 页内、可接受图片化 PPTX。
- **不适用**：品牌汇报、需要逐字改稿、复杂图表。
- **质量门**：标题是结论句；每页不超过 1 个核心信息；字号 ≥ 18pt（投影）；无溢出；字体在目标机器存在。
- **成本**：分钟级；几乎零工程。

### W2 模板注入线（python-pptx / pptx-automizer）

```
品牌 PPTX ──> 版式/占位符清单 ──> 内容 JSON ──> 填充/复制 ──> 渲染 ──> 检查 ──> 交付
```

- **适用**：企业/学院固定模板、8–20 页、强品牌一致性、需要原生可编辑。
- **不适用**：没有合格模板；版式需要大幅重构；动画/复杂 SmartArt。
- **质量门**：占位符覆盖率 100%；溢出 0；字体替代 0；图表数据可改；母版/版式继承正确；备注保留。
- **成本**：2–5 人日/模板；之后每页分钟级。
- **关键**：模板不是“背景图”，而是**版式 API**：槽位、字号、行距、图表位、图片裁切规则都要显式化。

### W3 设计系统线（HTML/SVG → 原生 PPTX）

```
Design tokens ──> 页型组件 ──> HTML/SVG ──> 浏览器测量 ──> PptxGenJS/DrawingML 重建
                                                   │
                                                   └─> 渲染 ──> VLM/人审 ──> 定点修复
```

- **适用**：发布级视觉、没有合适模板、需要“设计自由度 + 可编辑”。
- **不适用**：10 页以内的小任务（成本过高）；团队没有前端/设计能力。
- **质量门**：元素级重建率 ≥ 80%；整页回退 ≤ 10%；对比度 ≥ 4.5:1（正文）；字号/网格/间距符合 token；中英文断行复检。
- **成本**：5–15 人日/主题；每页 20–60 分钟（含评审）。
- **关键**：浏览器与 PowerPoint 的文本度量不同，必须“测量 → 重建 → 渲染 → 对比”闭环；不能假设 DOM 布局等于 PPTX 布局。

### W4 Agent 全自动线（PPTAgent / PPT Master 式）

```
资料 ──> 研究/事实表 ──> 大纲 ──> 页计划 ──> 页面源(HTML/SVG) ──> 渲染
                                              │
                                              ├─> 视觉评审（VLM/人）──> 缺陷清单
                                              └─> 定点修复 ──> 复审 ──> 导出
```

- **适用**：无模板、从资料快速出草稿、研究/论文/报告。
- **不适用**：强品牌、强合规、要求一次成稿。
- **质量门**：源与导出分别审；修改后旧评审失效；每页必须有“结论 + 证据”；视觉缺陷必须定位到元素；失败页允许回退但必须记录。
- **成本**：token/重试成本高；需要人工做最后一公里。

### W5 平台/API 线（Presenton + n8n/Dify）

```
表单/数据库 ──> API/MCP ──> 生成任务 ──> 轮询/回调 ──> 存储 ──> 通知 ──> 人工审核
```

- **适用**：批量、运营化、多用户、自助生成。
- **不适用**：高度定制、涉密、无法外发数据。
- **质量门**：任务状态可追踪；失败可重试；输出带模板版本与模型版本；审核队列；成本上限。
- **风险**：导出核心许可、数据外发、模型价格波动、并发与限流。

### W6 存量改造线（提取 → 重排 → 回写）

```
既有 PPTX ──> 文本/结构提取 ──> 问题清单 ──> 版式重排/美化 ──> 回写 ──> 对照渲染
```

- **适用**：已有 deck 的“救火”、品牌升级、答辩稿美化。
- **不适用**：源文件严重损坏；动画/嵌入对象复杂。
- **质量门**：内容零丢失；页码/章节结构保持；改动可 diff；原文件备份；逐页对照。
- **工具**：python-pptx（保守修改）、pptx-automizer（复制页）、PPT Master 的 `edit-native-pptx`（保源往返）。

### 6.7 工作流选择表

| 场景 | 首选 | 次选 | 不建议 |
|---|---|---|---|
| 10 页内技术分享 | W1 Marp/Slidev | W3 | W2（没有模板时） |
| 企业品牌汇报 | W2 模板注入 | W3 + 品牌 token | W1（图片化） |
| 学术答辩 | W2（学院模板） | W3（图表多） | W5（数据外发） |
| 数据密集报告 | W2 + 原生图表 | W3 | W1（图表弱） |
| 发布级视觉 | W3 | W4 | W1/W2 |
| 批量运营 | W5 | W2 + 队列 | W4（成本不可控） |
| 存量改造 | W6 | W2 | W4（重建成本高） |

## 7. 关键工程专题

### 7.1 可编辑性光谱 E0–E4

“支持 PPTX”没有意义，必须定义可编辑层级：

| 级别 | 定义 | 判定方法 | 典型来源 |
|---|---|---|---|
| **E0** | 每页只有一张整页图片 | 解包后每页仅 `<p:pic>` 或无文本 | Marp 默认、Paper2Slides、网页截图 |
| **E1** | 背景图 + 可编辑文本框 | 有 `<a:t>` 文本，但背景是图片 | 部分模板填充、图片化导出的补丁 |
| **E2** | 文本 + 基础形状可编辑；图表/表格是图片 | 形状数 > 0，chart part = 0 | 轻量 HTML→PPTX |
| **E3** | 原生形状/表格/组合；图表为 SVG/图片 | 有 table/shape，chart part = 0 | Slidev editable、PPTist 导出 |
| **E4** | 原生形状 + 原生图表（含数据工作簿）+ 母版/版式继承 | 有 chart XML + embedded workbook；layout 关系存在 | PptxGenJS、python-pptx、PPT Master、模板注入 |

**三个可计算指标**：

- **可编辑覆盖率** = Σ(可编辑对象) / Σ(可见对象)，按类型加权（文本 1.0、形状 0.8、表格 1.0、图表 1.2、图片 0）；
- **数据可编辑率** = 原生 chart 数 / 图表总数；
- **母版继承率** = 使用 layout 的页数 / 总页数。

**选型顺序**：先定目标 E 级别，再选路线。要求 E4 却选 Marp 默认，是需求错配；只求展示却强上 E4，是成本浪费。

### 7.2 布局与溢出：为什么模型做不好

模型擅长“写内容”，不擅长“在 13.333×7.5 英寸里做带字体度量的二维布局”。根因有三：

1. **度量不可见**：模型看不到字体的 advance width、行高、断行禁则；
2. **约束太多**：字号、行距、段距、边距、图片裁切、图表标签相互耦合；
3. **反馈太慢**：生成 → 打开 PowerPoint → 发现溢出，循环成本高。

三种解法，按成本从低到高：

| 解法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **模板槽位** | 版式固定，只填内容；超长走“缩字号/拆页”规则 | 稳、快、品牌一致 | 设计自由度低 |
| **约束布局引擎** | 用 Flex/Grid/自动布局计算位置，再导出 | 兼顾自由度与稳定 | 需要前端能力 |
| **测量-回填** | 浏览器/COM 测量文本边界，回填坐标；溢出则缩字号/拆页 | 接近真实渲染 | 跨引擎差异、实现复杂 |

**工程建议**：不要追求“任意内容自动排版”。先做 8–12 个页型组件，每个组件定义“容量上限 + 溢出策略 + 最小字号”，让模型在组件内填内容。

### 7.3 模板工程：模板即 API

高质量模板不是“好看的背景”，而是一套契约：

- **母版/版式**：封面、目录、章节、内容、数据、对比、结尾；
- **占位符**：标题、副标题、正文、图注、来源、页码；
- **容量**：每个占位符的最大字数/行数；
- **溢出策略**：缩字号、拆页、截断（禁止静默截断）；
- **图表位**：原生 chart 的类别数/系列数上限；
- **图片位**：裁切比例、最小分辨率、版权字段；
- **主题**：字体栈、色板、间距、圆角/线宽。

**模板版本化**：每次模板变更都要有版本号、变更说明、回归样本；生成任务记录模板版本，否则无法复现。

### 7.4 中文排版：被低估的失败源

中文 PPT 的常见问题与对策：

| 问题 | 表现 | 对策 |
|---|---|---|
| 字体缺失 | 用宋体代替思源黑体，字宽/行高全变 | 字体白名单 + 目标机器检查 + 渲染复检 |
| 字重不对 | 标题用 Regular，层级塌陷 | 明确 Bold/Semibold；不要依赖“加粗”伪字重 |
| 标点挤压 | 中英文之间空隙过大/过小 | 统一中西文间距规则；避免全角空格 |
| 断行禁则 | 行首标点、行尾左括号 | 使用支持 CJK 禁则的引擎；人工复检 |
| 行距 | 1.2 倍行距在 PPT 中显得松散/拥挤 | 按字号设定固定行距，不用“倍数”通吃 |
| 度量差异 | 浏览器换行与 PowerPoint 不同 | 以 PowerPoint 渲染为准；保留 10% 余量 |

**字体嵌入**：PPTX 本身支持“嵌入字体”，但主流生成库（PptxGenJS、python-pptx）不提供该能力，且中文字体体积大、许可证常禁止嵌入。因此工程上通常按“不嵌入”处理：跨机器交付必须确认对方有字体，或把关键文字转曲/图片（但会牺牲可编辑性）。

### 7.5 图表：看起来对 ≠ 数据可编辑

- **原生 chart**（E4）：有 chart XML + embedded workbook，双击可改数据；适合数据报告。
- **SVG/图片 chart**（E3 以下）：视觉可控，但不能改数据；适合“一次性发布”。
- **假图表**：用形状拼的柱状图，看起来像，但没有数据语义；审稿时要单独标记。

**检查点**：chart part 是否存在；embedded workbook 是否可打开；轴/标签是否碰撞；系列颜色是否可区分；数据与来源是否一致；单位/小数位是否统一。

### 7.6 视觉评审闭环

一个可用的闭环至少四步：

1. **渲染**：目标渲染器（PowerPoint COM 优先，LibreOffice 次选）输出逐页 PNG；
2. **评审**：VLM + 人，按 rubric 输出**结构化缺陷**（页码、元素、类型、严重度、证据）；
3. **修复**：只改被点名的元素，不整页重生成；
4. **复审**：重新渲染，对比修复前后；修改使旧评审失效。

**VLM 的盲区**：小字（<12pt）、细线、低对比度、遮挡、表格单元格溢出、图表标签碰撞。不要让 VLM 单独做终审；它适合“发现问题”，不适合“证明没问题”。

### 7.7 评估与自建基准

建议的 20 页中文基准集（与既有研究一致，可直接复用）：

| 页型 | 考察点 |
|---|---|
| 封面 | 标题层级、副标题、日期/作者 |
| 长标题 | 两行/三行、断行、字号自适应 |
| 中英混排 | 字距、行距、标点 |
| 双栏 | 栏宽、对齐、阅读顺序 |
| 流程图 | 连接符、节点、箭头 |
| 原生柱线图 | 数据、轴、标签、图例 |
| 数据表 | 列宽、单元格溢出、表头 |
| 公式 | OMML/LaTeX 渲染 |
| 图片裁切 | 比例、焦点、版权 |
| 结论页 | 行动标题、请求 |

**评分卡**（每页二元项，机器可验 + 人可验）：

- 内容：事实有来源、数字一致、标题是结论；
- 结构：页型正确、阅读顺序正确、无孤立页；
- 视觉：无溢出、无遮挡、对比度达标、字号达标、网格对齐；
- 工程：E 级别达标、字体存在、chart 可编辑、文件可打开；
- 成本：生成时间、返工次数、人工分钟数。

**硬门禁**（任一失败即整页不通过）：文本裁切、内容遮挡、数据与来源不一致、整页被截图替代但声明可编辑。

### 8.1 选型矩阵

| 场景 | 首选 | 次选 | 避免 | 理由 |

| 10 页内技术分享 | Marp / Slidev | reveal.js | PPT Master | 速度优先，图片化可接受 |

| 发布级视觉 | SVG/HTML → PPTX（PPT Master/Slidev editable） | 自研 Playwright+PptxGenJS | 纯 Agent | 设计自由度 + 可编辑 |

| 存量改造 | python-pptx / pptx-automizer | PPT Master edit-native | 重新生成 | 保内容/保结构 |
| 离线/保密 | 本地模型 + 本地引擎（Ollama + PptxGenJS） | Slidev 本地 | 云 API | 数据不出境 |

### 8.2 决策树

```
必须原生可编辑（E3+）？
├─ 否 → 只需展示/打印？
│        ├─ 是 → Marp / Slidev / reveal.js（HTML/PDF）
│        └─ 否 → 仍建议 PDF，避免“假 PPTX”
└─ 是 → 有品牌模板？
         ├─ 有 → 模板覆盖率 ≥ 80%？
         │        ├─ 是 → W2 模板注入（pptx-automizer / python-pptx）
         │        └─ 否 → W3 设计系统 + 模板混合
         └─ 无 → 设计感要求？
                  ├─ 高 → W3（SVG/HTML → 原生对象；PPT Master / Slidev editable / 自研）
                  ├─ 中 → 组件库 + PptxGenJS（8–12 个页型）
                  └─ 低 → W1 Markdown（接受 E0–E2）

另加两个正交问题：
- 批量/无人值守？ → 加 API/MCP + 队列 + 审核队列
- 涉密/不能外发？ → 本地模型 + 本地渲染，禁用云 API
```

## 9. 接入现有六阶段工作流的映射

现有 `ppt-workflow` 的阶段是：`intake → outline → template → compose → polish → review`。外部项目不应替换阶段，而应成为阶段内的“能力供应商”：

| 阶段 | 可接入能力 | 代表项目 | 接入方式 | 优先级 |
|---|---|---|---|---|
| **intake** | 文档解析（PDF/DOCX/PPTX/图片） | MarkItDown、MinerU、PPTAgent 的 any2markdown | 本地 CLI/MCP，输出 Markdown + 图片 + 来源 | P1 |
| **outline** | 行动标题、幽灵 deck、论证结构 | academic-pptx-skill | 规则移植到提示词/检查器 | **P0** |
| **template** | 模板蒸馏、版式/占位符清单 | PPTist schema、PPT Master create-template、Presenton custom template | 离线分析 + 人工审核 | P1 |
| **compose** | 原生对象生成 | PptxGenJS（主）、python-pptx（模板）、pptx-automizer（复制） | 现有引擎 + 新适配器 | **P0** |
| **compose（对照）** | SVG → DrawingML | PPT Master | 独立 POC，不进入主线 | P2 |
| **polish** | DOM 测量、版式规则 | Slidev editable、visual-explainer | 参考实现，提取测量/布局规则 | P1 |
| **review** | 双评审、rubric、硬门禁 | PPTAgent、PresentBench、PPTBench | 评审合同 + 检查器 | **P0** |

### 9.1 明确不建议接入的

| 项目 | 原因 |
|---|---|
| **Presenton 全平台** | 导出核心 `@presenton/export-core` 的许可证/源码未闭环；运维重（Docker/Chromium/DB） |
| **PPTist 嵌入产品** | AGPL-3.0，闭源商用需授权；适合参考，不适合直接嵌 |
| **Anthropic pptx skill** | 文件级许可禁止衍生/复制；只能作能力对照 |
| **Paper2Slides** | 输出 PNG/PDF，不是可编辑 PPTX；与主线目标不符 |
| **PPTAgent 安装栈** | Linux/WSL/macOS + LibreOffice/Playwright，Windows 主线接入成本高；借流程即可 |

### 9.2 接入顺序建议

1. **先接 review**：把 PresentBench 式二元清单 + PPTAgent 的“源/导出双审”接进现有 review，立刻提升交付质量。
2. **再接 outline**：academic-pptx-skill 的行动标题/幽灵 deck 规则，成本最低、收益最大。
3. **然后 compose 适配器**：pptx-automizer 做模板通道 POC；PPT Master 做 SVG 编译 POC（二选一先做）。
4. **最后考虑 intake/polish**：文档解析与 DOM 测量是“锦上添花”，不是瓶颈。

## 10. 90 天实施路线

> 时间为建议值，按团队规模与既有资产调整；每个阶段必须以“可复现产物 + 退出条件”结束，不能以“跑通一次”代替验收。

| 阶段 | 时间 | 目标 | 交付物 | 退出条件 |
|---|---|---|---|---|
| **P0 基准** | 第 1–2 周 | 冻结 20 页中文测试集与 E0–E4 口径 | 测试集、评分卡、基线报告 | 每页有来源与预期 E 级别 |
| **P1 模板通道** | 第 3–4 周 | 验证 pptx-automizer vs python-pptx | 模板适配器 POC、回归报告 | 占位符覆盖 100%，溢出 0 |
| **P2 设计源** | 第 5–8 周 | 验证 SVG/HTML → 原生对象 | PPT Master 或自研 POC、回退清单 | 元素级重建 ≥ 80%，回退 ≤ 10% |
| **P3 评审** | 第 7–9 周 | 双审 + 二元清单 + 硬门禁 | review 合同、检查器、缺陷库 | 真实 10 页任务一次通过率 ≥ 70% |
| **P4 运营化** | 第 10–12 周 | 批量/API/成本 | 任务队列、成本报表、SOP | 单页人工分钟数下降 ≥ 30% |

**停止条件（kill criteria）**：

- 目标 E4 但实测可编辑覆盖率 < 70%；
- 单页返工 > 10 分钟，且连续 3 个任务无改善；
- 模板通道在 3 份真实模板上关系部件丢失；
- 视觉评审无法定位到元素，仍靠“整页重生成”。

## 11. 风险与合规

| 风险 | 具体表现 | 处置 |
|---|---|---|
| **许可证** | PPTist AGPL；Anthropic pptx 禁止衍生；Presenton export-core 待核；PPT Master 可选 PyMuPDF AGPL | 文件级许可清单；固定 commit/tag；不使用未核清的导出包 |
| **数据外发** | 云模型/云平台接收内部资料 | 本地模型/本地渲染；脱敏；数据分类 |
| **字体** | 商用字体未授权；跨机缺失 | 字体白名单；开源字体（思源/Noto）；授权记录 |
| **图片/模板** | 网络图片版权；会员模板再分发 | 来源表；CC0/购买授权；模板仅本地使用 |
| **事实幻觉** | 数字/引用编造 | 来源表 + 人工核对；禁止无源数字 |
| **版本漂移** | main 分支/最新版行为变化 | 锁版本；回归样本；SBOM |
| **单维护者** | 项目停更/转向 | 不把单一项目当唯一底座；保留回退路线 |

## 12. 结论与判断

1. **2026 年的竞争点已经从“能不能生成”转向“能不能稳定交付可编辑、可验收的 deck”。** Slidev/Marp 的 editable、PPT Master 的 SVG 编译、PPTAgent 的双评审，都是同一方向的不同答案。
2. **模板注入仍是企业场景的最高 ROI。** 它同时满足品牌一致性、E4 可编辑、低边际成本；自由设计只在“没有模板/发布级视觉”时值得投入。
3. **Agent 的价值在编排与评审，不在替代设计系统。** 没有约束、没有渲染回环、没有失败恢复的 Agent，产出的是“看似完整、不可复现”的草稿。
4. **插件层的正确姿势是“少而稳的原语”。** MCP/Skill 不是越多越好；`measure/render/lint/export` 四件事做好，比 34 个工具更有用。
5. **评估必须二元化、可定位、分输入类型。** PDF 评审不能证明 PPTX 可编辑；总分不能替代硬门禁；VLM 不能单独终审。
6. **对本项目**：保持 PptxGenJS 主引擎与六阶段工作流；优先接 review 与 outline 的外部方法；模板通道与 SVG 编译各做一个 POC；不引入完整平台替换现有实现。

**一句话**：把开源项目当**零件**，不当**平台**；把质量当**乘法**，不当**总分**；把“可编辑”当**光谱**，不当**布尔值**。
