# 建议与落地路线图

> 面向现有 `ppt-workflow` 六阶段（`intake → outline → template → compose → polish → review`）的增补建议。  
> 本文不改变已审核的主方案，只回答三个问题：**先接什么、怎么验证、什么时候停**。

---

## 0. 结论先行

1. **保持 PptxGenJS 主引擎与六阶段结构**，不引入完整平台替换。
2. **接入顺序：review → outline → template POC → 设计源 POC →（可选）平台化**。
3. **每条能力线都必须有基准集、硬门禁与停止条件**；没有这三样，不要进入下一阶段。

---

## 1. 目标与约束

| 维度 | 现状 | 目标 | 约束 |
|---|---|---|---|
| 平台 | Windows + PowerPoint COM；WPS 已验证局部能力 | 同一套产物在 PowerPoint 稳定打开 | 不假设跨平台渲染一致 |
| 语言 | 中文优先 | 中文断行、字体、标点可复检 | 字体不嵌入时需目标机器有字体 |
| 页数 | 8–20 页 | 同左 | 不做“任意长度自动排版” |
| 可编辑 | 原生文本/形状/常见图表 | 对外 E4；内部草稿可 E3 | 图表必须数据可改 |
| 数据 | 本地处理 | 涉密材料不出本机 | 云 API 仅用于非敏感任务 |
| 质量 | 已有 linter/渲染/回归 | 可定位缺陷 + 硬门禁 + 一次通过率 | 不以“跑通”代替验收 |

---

## 2. 目标架构

```
Brief ─► intake ─► outline ─► template ─► compose ─► polish ─► review ─► deliver
          │          │           │            │          │         │
          │          │           │            │          │         └─ 二元清单 / 硬门禁 / 双审
          │          │           │            │          └─ DOM 测量 / 版式规则
          │          │           │            └─ PptxGenJS / pptx-automizer / SVG 编译
          │          │           └─ 模板版本 / 槽位 / 容量
          │          └─ action title / ghost deck / 证据 ID
          └─ MarkItDown / MinerU + 来源表
```

**原则**：每个阶段只做一件事；外部项目是阶段内的“能力供应商”，不是新的阶段。

---

## 3. 六阶段接入清单

| 阶段 | 接入能力 | 代表项目 | 优先级 | 交付物 | 退出条件 |
|---|---|---|---|---|---|
| **intake** | 文档解析（PDF/DOCX/PPTX/图片） | MarkItDown、MinerU | P1 | 来源表 + Markdown + 图片 | 关键页可定位到原文 |
| **outline** | 行动标题、幽灵 deck、论证结构 | academic-pptx-skill | **P0** | 标题规则 + 检查清单 | 标题串起来能讲完整故事 |
| **template** | 模板审计、槽位映射、复制/填充 | pptx-automizer、python-pptx | P1 | 模板适配器 + 映射表 | 3 份真实模板通过 |
| **compose** | 原生对象生成 | PptxGenJS（主）、pptx-automizer（模板） | **P0** | 现有引擎 + 新适配器 | E4 覆盖率达标 |
| **polish** | DOM 测量、版式与信息设计规则 | Slidev editable、visual-explainer | P1 | 测量脚本 + 规则 | 溢出/遮挡 0 |
| **review** | 双审、二元清单、硬门禁 | PPTAgent、PresentBench、PPTBench | **P0** | 评审合同 + 缺陷库 | 一次通过率 ≥ 70% |

**为什么 review 先于 compose**：生成质量的提升需要新依赖与新流程；评审合同的提升只需要规则与报告模板，成本最低、对交付影响最大。

## 4. 三个 POC

### POC-1：模板通道（2 周）

**目的**：证明“真实品牌模板 → E4 原生 PPTX”可稳定复现。

| 项 | 内容 |
|---|---|
| 输入 | 3 份真实模板（学院答辩 / 企业汇报 / 现有 WPS 模板）+ 同一份 10 页内容 JSON |
| 对照 A | `pptx-automizer`：复制页/母版/图表，填充文本 |
| 对照 B | `python-pptx`：按占位符保守填充 |
| 步骤 | ① 模板审计（master/layout/占位符/图表/notes）② 建槽位映射 ③ 填充/复制 ④ 渲染 ⑤ 结构检查 |
| 指标 | 槽位覆盖 100%；关系部件 0 丢失；溢出 0；字体替代 0；图表数据可改；单页人工分钟 |
| 停止 | 2/3 模板关系部件丢失，或槽位覆盖 < 80% → 回退 python-pptx 保守填充 |
| 产出 | 适配器、映射表、回归报告、失败样本 |

**注意**：动画不在 `pptx-automizer` 支持范围；含动画模板先隔离，不进入默认稳定通路。

### POC-2：设计源（3 周）

**目的**：判断“设计自由度 + E4”是否值得投入。

| 项 | 内容 |
|---|---|
| 输入 | 5 页固定设计（封面 / 长标题 / 图表 / 流程 / 表格）+ design tokens |
| 对照 A | `PPT Master`：受约束 SVG → DrawingML |
| 对照 B | 自研 Playwright 测量 + PptxGenJS 重建 |
| 对照 C（可选） | `Slidev --format pptx-editable` |
| 指标 | 元素级重建率 ≥ 80%；整页回退 ≤ 10%；文本可编辑率 ≥ 90%；与设计稿结构差；单页分钟 |
| 停止 | 重建 < 70%，或回退 > 20%，或单页 > 30 分钟 |
| 产出 | 流水线、回退清单、成本模型 |

**注意**：浏览器度量 ≠ PowerPoint 度量；必须“测量 → 重建 → 渲染 → 对比”四步闭环。

### POC-3：评审合同（2 周）

**目的**：把“渲染出来看一眼”变成可复现、可定位、可统计的评审。

| 项 | 内容 |
|---|---|
| 输入 | 10 页真实 deck + 来源材料 |
| 方法 | PresentBench 式 20–30 项二元清单 + PPTAgent 式源/导出双审 + PPTBench 式硬门禁 |
| 指标 | 缺陷定位率（到页/元素）≥ 90%；误报率；一次通过率 ≥ 70%；人工分钟；评审一致性 |
| 停止 | 缺陷无法定位到元素，或误报率 > 30% → 只做人工评审，不上自动评分 |
| 产出 | 评审清单、缺陷库、报告模板 |

**硬门禁示例**：文本裁切、内容遮挡、数据与来源不一致、声明可编辑但整页是截图——任一失败即整页不通过。

## 5. 90 天计划

| 周 | 任务 | 交付物 | 退出条件 |
|---|---|---|---|
| W1 | 冻结 20 页中文测试集；定义 E0–E4；记录基线 | 测试集、口径、基线报告 | 每页有来源与预期 E 级别 |
| W2 | 建立评分卡；跑一遍现有引擎 | 评分卡、缺陷库 v1 | 基线可复现 |
| W3 | 模板审计；建 3 份模板的槽位映射 | 模板审计表、映射表 | 槽位可枚举 |
| W4 | POC-1 跑通并对照 A/B | 适配器、回归报告 | 槽位覆盖 100%、溢出 0 |
| W5 | 评审清单 v1；硬门禁定义 | 评审合同 | 每项可二元判定 |
| W6 | POC-3 在 10 页真实任务上运行 | 评审报告、缺陷统计 | 一次通过率 ≥ 70% |
| W7 | design tokens；5 页固定设计 | 设计源、tokens | 页面可独立渲染 |
| W8 | POC-2 跑通并对照 A/B | 流水线、回退清单 | 重建 ≥ 80%、回退 ≤ 10% |
| W9 | 10 页真实任务端到端 | 完整交付包 | 全链路无人工改稿 |
| W10 | 修复与复跑 | 修复记录、二次报告 | 缺陷闭环 |
| W11 | 成本核算（token、人工分钟、返工） | 成本模型 | 单页人工分钟下降 ≥ 30% |
| W12 | Go/No-Go：是否平台化 | 决策备忘 | 三项拍板问题有结论 |

> 时间为建议值；每个阶段没有退出条件就不进入下一阶段。

## 6. 验收指标

### 6.1 可编辑性 E0–E4

| 级别 | 定义 | 判定 |
|---|---|---|
| E0 | 整页图片 | 每页仅图片或无文本 |
| E1 | 背景图 + 可编辑文本 | 有 `<a:t>`，背景为图片 |
| E2 | 文本 + 基础形状；图表/表格为图片 | 有 shape，无 chart part |
| E3 | 原生形状/表格；图表为 SVG/图片 | 有 table/shape，无 chart part |
| E4 | 原生形状 + 原生图表 + 母版/版式 | 有 chart XML + embedded workbook + layout 关系 |

**三个指标**：

- 可编辑覆盖率 = 可编辑对象 / 可见对象（类型加权）；
- 数据可编辑率 = 原生 chart 数 / 图表总数；
- 母版继承率 = 使用 layout 的页数 / 总页数。

### 6.2 硬门禁（任一失败即整页不通过）

- 文本裁切 / 内容遮挡；
- 数据与来源不一致；
- 声明可编辑但整页是截图；
- 文件无法在目标 PowerPoint 打开或需要修复；
- 字体替代导致版式明显变化（需记录并人工确认）。

### 6.3 效率指标

| 指标 | 基线 | 目标 |
|---|---|---|
| 一次通过率 | 待测 | ≥ 70% |
| 单页人工分钟 | 待测 | 下降 ≥ 30% |
| 整页回退率 | 待测 | ≤ 10% |
| 返工次数/页 | 待测 | ≤ 1 |
| 评审缺陷定位率 | 待测 | ≥ 90% |

### 6.4 缺陷分类

| 编号 | 类型 | 例子 | 检测 | 责任 |
|---|---|---|---|---|
| C1 | 内容 | 数字错、引用错、结论过期 | 来源表 + 人工 | 内容 |
| C2 | 结构 | 标题是名词标签、页间无递进 | 幽灵 deck | 内容/设计 |
| C3 | 视觉 | 溢出、遮挡、对比度不足、字号过小 | linter + 渲染 + 人 | 设计 |
| C4 | 工程 | 字体回退、图表不可改、文件修复 | 结构检查 + COM | 工程 |

## 7. 风险与许可证

| 风险 | 触发条件 | 处置 |
|---|---|---|
| **Presenton export-core 许可未闭环** | 计划接入平台/API | 先核 tgz 的 LICENSE/NOTICE/源码/哈希；不通过则不接入 |
| **PPTist AGPL** | 想嵌入产品 | 闭源商用需商业授权；否则只作参考 |
| **Anthropic pptx 禁止衍生** | 想复用其 skill | 只作能力对照，不复制文本/代码 |
| **PyMuPDF AGPL** | 使用 PPT Master 的 PDF 转换 | 单独评估；可替换或隔离 |
| **字体许可** | 商用字体、跨机交付 | 字体白名单 + 授权记录；优先开源字体 |
| **图片/模板版权** | 网络图、会员模板 | 来源表 + 授权；模板仅本地使用 |
| **数据外发** | 云模型/云平台 | 脱敏；涉密任务本地模型 + 本地渲染 |
| **版本漂移** | 跟随 main/最新版 | 固定 commit/tag；锁文件；回归样本 |
| **单维护者** | 依赖单一项目 | 保留回退路线；不把单一项目当唯一底座 |
| **COM 不稳定** | 重复自动化 | 进程隔离、超时、重试；渲染与测量分开跑 |

## 8. 不做清单

1. **不用 star 数选型**：星数只表示社区规模，不表示质量/稳定/许可。
2. **不把 PDF 评审当可编辑证明**：PresentBench 的输入是 PDF，不能证明 PPTX 可编辑。
3. **不做“万能布局”**：先做 8–12 个页型组件，容量与溢出策略显式化。
4. **不引入完整平台替换六阶段**：平台化只在批量需求与许可审计都通过后考虑。
5. **不把 VLM 当终审**：它适合发现问题，不适合证明没问题；小字/细线/遮挡是盲区。
6. **不在没有基准集时比较项目**：没有固定输入与评分卡，任何“更好”都不可复现。
7. **不分发未授权的模板/字体/图片**：模板会员资源仅限许可范围内本地使用。

## 9. 三个待拍板问题

| 问题 | 选项 | 建议 | 影响 |
|---|---|---|---|
| **目标 E 级别** | E3 / E4 | 对外 E4，内部草稿 E3 | 决定是否投入模板/原生图表 |
| **模板 vs 自由设计** | 模板注入 / 设计系统线 | 模板优先 | 决定 2–5 人日/模板还是 5–15 人日/主题 |
| **本地 vs 平台** | 本地六阶段 / Presenton | 本优先 | 决定是否承担 export-core 审计与运维 |

**拍板后写在任务合同里**：目标 E 级别、模板来源、是否允许云 API、停止条件。否则每个任务都会重新争论一遍。

## 10. 附：一页决策表

| 如果你的情况是… | 选… | 因为… |
|---|---|---|
| 10 页内、技术分享、可接受图片化 | W1 Marp/Slidev | 速度最快，成本最低 |
| 有合格品牌模板、8–20 页 | W2 模板注入 | 质量/成本/可编辑性同时占优 |
| 没有模板、发布级视觉 | W3 设计系统线 | 唯一能兼顾自由度与 E4 的路线 |
| 需要批量、多用户、自助 | W5 Presenton + n8n | 有 API/MCP，但先审计 export-core |
| 已有 deck 要救火 | W6 提取→重排→回写 | 保内容/结构，风险最低 |
| 只要视觉草稿/海报 | Paper2Slides | 快，但输出 PNG/PDF，不可编辑 |
