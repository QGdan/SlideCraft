# 对应现有六阶段的迁移设计

这是一份下一阶段实现草案。本轮生产代码、已安装 Skill、原客户 PPT、已有样稿均未改动。

## 已经具备的能力，应继续复用

| 现有模块 | 已具备 | 本轮决定 |
|---|---|---|
| `production_materials.py` | 真实正文、讲稿、视觉用途；按页准备和冻结素材包 | 增加内容关系和表达选择，不再另建素材目录协议 |
| `content.py` | 数值、公式、来源、原生图表缓存和工作簿绑定检查 | 保留；外部图表数据适配也接入这里 |
| `online_assets.py` / `asset_placement.py` | 检索、下载、来源、裁切、入页 | 改进检索意图和构图匹配，不重复做“接通接口”证明 |
| `blueprints.py` / `template_resources.py` | 结构化模板、对象/模板关系盘点 | 补语义槽位与容量适配，继续复用 WPS/Office 模板路径 |
| `module_library.py` / `exhibits.py` | 原生步骤、行动、对照、时间线模块 | 扩大结构与布局配方，不用装饰图标掩盖关系缺失 |
| `editorial_builder.py` | 场景编译、必要规范化、原生对象检查 | 保留为主出口；补足渲染能力和明确的支持范围 |
| `stages.py` 与六个 Skill | 分工、交接和阶段审核 | 继续沿用；新增能力分配给原有阶段 |

## 差距一：有详细大纲，但缺少可执行的内容关系

`validate_brief()` 已要求每页真实正文、讲稿和视觉任务，这比只有目录成熟。当前视觉任务包含 kind/purpose/composition_hint/search_terms/source_refs/fact_refs，却不显式表达项目间的关系，也没有把对应的结构选择送到构图编译器。现阶段不是“缺一个大纲阶段”，而是需要让大纲对制作更有帮助。

建议在详细大纲增加少量可选字段：

```json
{
  "reading_order": ["主张", "证据", "解释"],
  "relationship": {
    "kind": "comparison",
    "items": ["现状", "建议"],
    "basis": "按相同维度对照，不能混用不同时间口径"
  },
  "dominant_evidence": "本页已准备的证据对象ID",
  "layout_candidates": ["同维度对照", "证据加解释"],
  "layout_reason": "证据数量和文字体量适合左右对应"
}
```

这是建议格式，不是已实现接口。事实与关系必须来自材料；大纲不写任意坐标，不规定每个对象必须是什么装饰形状。由 ppt-outline 负责信息模型，ppt-template/ppt-compose 负责表达选择。

## 差距二：现成页型能用，但构图选择有限

`design.py` 的基础页型使用固定区域；`compose_page()` 对指标数量、列数和步骤数也有固定容量。`module_library.py` 当前目录有4个模块；注册的 campus-editorial-v1 蓝图有5个语义布局。前两轮 editorial-wine 样稿已保存为参考候选，但不是被自动选用的布局库。应把真实表达能力接到工作流里，而非继续积累独立的样稿脚本。

建议第一批构图配方：

| 配方 | 内容关系 | 核心输出 | 选择依据 |
|---|---|---|---|
| 证据与解释 | 一个结论由一组证据支撑 | 大证据区+结论/解释区 | 图表/图像是否需要占主要面积 |
| 同维度对照 | 两种选择按相同维度比较 | 对齐的成组文字、图或原生表格 | 对照维度是否真实对应 |
| 步骤与产出 | 顺序动作生成中间产物 | 节点、连线、对应产出 | 顺序、可分支性和说明长度 |
| 层级与归属 | 明确父子或成员关系 | 原生节点与连接线 | 层数、节点数和关系标签 |
| 趋势与事件 | 序列变化及来源中的事件 | 原生折线+关键点解释 | 时间顺序、单位和真实注释 |
| 图片叙事 | 主题/场景与短解释 | 保留焦点的图片+原生文案 | 原图画幅、主体、文字体量 |

每项先准备短、中、长三种内容的真实样例；给出替换规则、容量与不适用条件。配方可以有不同构图，但不为了防重复而机械旋转。整套需保持字体、角色色、边界和图形语言连续。

## 差距三：图形支持声明与一个编译分支之间存在空档

`engine/editorial_build.cjs:28` 将 shape 统一画成矩形；`:30` 对 diagram/smartart 也只画一个矩形，没有消费其节点和关系。该分支不能实现语义关系图。其他路径通过 `exhibits.py` 提前展开普通文字和线条，不属于这一问题，不能笼统说整个项目都不支持关系图。

先处理两件事：

1. 对尚未实现的语义对象明确报不支持，避免生成一个矩形后把责任推给美化。
2. 首先实现常用原生形状、节点分组、直线/折线连接和关系标签，与对象映射一致。需要原生 SmartArt 数据部件时单独走已支持出口，不能把普通节点组叫 SmartArt。

这比立刻扩成几十种高级图表更贴近“元素单调”的实际问题。可学习 PPT Master 的形状与连接语义，但保持我们自己的受约束 scene-spec 和来源检查。

## 差距四：模板容量主要靠字符数，缺少文字与证据共同适配

`blueprints.py` 按字段字符数判断容量，`module_library.py` 有标题/正文长度上限；能防止过量输入，但相同字符数的中文、数字、英文单词在相同框中并不等宽。`editorial_build.cjs` 直接用既定几何写字，没有内容测量阶段。

学习 presentation-skill 的空间分配思路：先预留标题/来源，再以真实正文和字体估算主区；在允许的配方变体内调整比例。中文须支持按字和标点断行、混排单词边界，并最终看 PowerPoint 导图。放不下时先换表达、换配方或拆页，保留用户指定页数时再协商内容取舍，不能自动删项目或藏字。

## 差距五：素材已经能检索，但风格继承仍可强化

无需另造更大的本地图库。当前任务素材包已按页保存图片和原生图形的源/预览，应在选择前增加“视觉角色+画幅+主体留白+风格”的条件，使检索结果能服务页面构图。

可借鉴宝玉的统一风格块，但应用到单个素材：选定模板后把角色色、材质、线条、光照、主体风格写成同一份说明；所有新插画读取它。每个素材记录自己的用途、参考和提示词。图片类内部元素仍按位图处理；重要文字与数据留在原生对象层。

模板与素材可少量往返：大纲先定义需求和初步比例，素材阶段验证实际图片是否合适，模板代表页验证正文与素材容量；发现无法成立时回改受影响页，不把所有内容硬塞进先选好的壳。

## 落到六个 Skill

| 阶段 Skill | 下一轮应补的职责 | 可见输出 |
|---|---|---|
| ppt-intake | 识别主用途是投影讲述还是阅读留档，沿用已知需求 | 一份精简需求，不重复访谈 |
| ppt-outline | 主张、证据、正文、讲稿、信息关系与图型理由 | 可以直接指导制作的逐页说明 |
| ppt-template | 检索候选，真实内容试排，选择完整视觉系统 | 封面/正文/数据代表页和容量说明 |
| ppt-compose | 按关系选择已实现的原生配方，使用任务素材包 | 可编辑 PPT 与稳定对象映射 |
| ppt-polish | 调整比例、阅读顺序、裁切、注释和跨页节奏 | 针对具体页面的改善 |
| ppt-review | 看最终 PPT 导图与关键编辑对象 | 保留阶段审核；问题回到对应源对象 |

## 建议分三批实施，审核看实际页面

**第一批：关系建模+原生结构。** 给详细大纲补字段，处理 editorial 的占位分支，完成步骤/层级/对照中最常见的原生结构。审核一页关系图、一页步骤产出、一页对照，判断是否表达准确且可修改。

**第二批：内容适配+模板代表页。** 配方接入统一选择流程，补中文测量和来源区预留；同一份真实材料分别验证长正文、图表和图片页。审核选型是否合理，长内容是否被完整承载。

**第三批：素材风格继承+常用构图库。** 把统一风格说明接入素材准备与美化，做一套真正题材相关的短简报，审核跨页连贯性和素材是否帮助表达。样稿仅作为项目能力的证据。

拟迁移代码只挑许可明确、职责小且可解释的部分；记录具体来源和改动。实现前不更换默认引擎，不安装成批新 Skill，不新增每阶段都要过的复杂工程审批。保留必要构建/导图/关键数据核对，研发精力放在内容和表达上。
