# 质量升级工作流

## 两类任务

项目工程优化：计划 → 实现合同/引擎/接口 → 自动回归与命令检查 → Skill验证与同步 → 工程报告。具体PPT的大纲或模板审批不阻塞工程工作。

业务PPT制作：intake → outline → template → compose → polish → review；仍逐阶段取得真实用户认可。新任务需求中设置quality_profile: quality-v1，旧任务缺省为legacy。不要给旧批准件补字段或伪造重新认可。

## 命令和职责

```powershell
# 编译能力边界，归ppt-compose
.\.venv\Scripts\python.exe -m ppt_workflow capabilities

# 内容计划预检并生成未填写的任务专属审核清单，归ppt-review
.\.venv\Scripts\python.exe -m ppt_workflow quality-check --outline examples/quality-outline.json --plan examples/content-plan.json --out runs/new-quality-check

# 项目优化自动验证；不制作用户业务PPT
.\.venv\Scripts\python.exe scripts/verify_project_upgrade.py --node D:/node/node.exe --out ../10-项目自动化优化实施-20261018/new-verification
```

out必须全新。quality-check结构合法时返回needs_review/退出码2，代表待宿主执行语义及视觉审阅，不是失败，也不是审美通过。校验错误返回失败，报告逐项列出。命令不会调用隐藏模型或在线平台。

## 正式接入的质量合同

- outline：quality_plan附件使用schemas/content-plan.schema.json，逐页保存问题、主张类型、证据、推理、限制、视觉载体、案例标签和专属问题；附件哈希变化使审批失效。
- template：design-system中的semantic_layouts声明每个已登记布局的载体、正文容量、最小正文字号和图表容量。正文、数据、关系、案例页可有不同构图，不仅复制背景。
- compose：选用布局必须支持计划载体，实际文字/图表不得超出已批准容量。事实、来源、标题与上游一致。
- review：quality_review使用schemas/quality-review.schema.json，分别记录内容、设计、工程判断；每条任务问题需答复，已答复有证据，返修定位责任阶段，resolved必须有复查证据。绑定与最终渲染一致。

自动QA、三维审核和人工偏好各司其职。严重问题、unknown和警告不会被综合平均分覆盖。合同与规则代码也参与审批哈希，避免校验器改变后沿用旧结论。

## 0.1与0.2

0.1输入合同仍可读取，旧统一构建入口保留原图表限制。0.2增加横条、柱和折线，多类别/系列，语义选型与重点标注。百分比减法单位改为百分点；跨scope的同题选项需显式comparison_group且同来源、同期。这个声明仍需核实，不自动证明可比。

散点、饼、地图、瀑布等当前扩展编译器不支持，明确拒绝。原生图型、缓存、工作簿和显示格式分别核验，不将“画出了一个图”当作成功。

规则、Skill、schema或能力清单更新后，旧阶段批准会显示过期，需重新核对。历史文件没有被改写；读取兼容不等于旧审批可在新规则下直接使用。

## 自动化验证范围

全量回归含历史夹具；portable-smoke只验证可迁移子集。新图表测试生成并检查临时合成包，结束自动清理，不生成业务演示稿、不操作Office。源码结构、原生缓存和工作簿通过，不能代替后续目标软件渲染、编辑保存或用户审美验收。
