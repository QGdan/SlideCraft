# 从详细大纲到通用制作

2026-10-22。`brief-compose`归ppt-compose，把前三批能力连接起来。新任务不必再临时编写拼接文字、图表、图片的专用程序；作者和各阶段Skill仍负责内容、选材和设计判断。

## 在六阶段中如何使用

1. **需求、大纲**：完成并审核逐页主张、body_blocks、事实与视觉需求。图片有visual_direction，关系图有明确relationship。大纲页ID、主张、顺序是制作输入。
2. **素材准备**：模板Skill通过asset-plan组织检索与风格；制作Skill执行素材准备子任务并asset-record。原生关系、图表保留source+实际preview。material-pack封存到本任务“素材”目录。
3. **模板**：选定设计系统与布局，写一份brief-composition-request/1。这里只填写页面对应的visual_id、布局key和必要的排版标签，不重新复制正文。用真实素材生成代表页并交用户审核；不是修改大纲或签署事实。
4. **制作**：模板获批后由ppt-compose运行brief-compose。它从包中取对应页素材、从brief中取正文，输出原生PPT、deck-spec、对象映射和composition.json。
5. **美化、审核**：在本机PowerPoint/WPS查看导出图片与整套节奏，打磨后按原阶段交接。工具输出不代表已自动批准业务阶段。

大纲/素材/模板变化时重做相应下游，不覆盖旧任务。正文放不下会提示换布局或将拆页提案交回大纲，不静默改页数。准备素材所需的预览是预制件，不要把它当作已完成的整套PPT。

## 调用

在ppt-workflow项目虚拟环境运行：

```powershell
python -m ppt_workflow brief-compose --input runs/任务/composition-request.json --out runs/任务/composed --node D:/node/node.exe
```

输入和输出都在项目内，输出必须是runs下的新目录。使用现有Node路径；换机器时先确认实际运行环境。输出composition.json可作为原compose阶段的交接输入，正式提交仍需要已经批准的需求、大纲与模板，不会伪造这些批准。

请求字段：

```json
{
  "version":"brief-composition-request/1",
  "job_id":"new-brief",
  "outline":"runs/任务/outline.json",
  "materials_pack":"runs/任务/素材/manifest.json",
  "design_system":"runs/任务/design-system.json",
  "pages":[
    {
      "slide_id":"s1","visual_id":"scene","layout":"image-right",
      "kicker":"场景与安排","source_note":"场景来源与示意说明。",
      "sections":[
        {"body_index":0,"heading":"明确服务事项"},
        {"body_index":1,"heading":"整理对应材料"}
      ],
      "focus":{"x":0.9,"y":0.5}
    }
  ]
}
```

pages必须逐一对应全部大纲页并保持顺序。图片sections按body_index依次覆盖每一个正文块，不能漏、重排或再次输入另一份正文。heading是经作者确认的小标题，正文实际来自brief。focus可省略，默认居中；明确传值时仍需查看真实裁切。

原生关系页的选择只需slide_id、visual_id、layout、kicker、source_note；原生图表页不传source_note，沿用预制图表来源。两类页将brief正文放为标题下的一行说明，过长时要求重新选布局或改叙事。图表结论与数据仍来自准备片段的事实模板，不把它们复制成无绑定的普通数字文本。

## 当前支持

- 单视觉配方保持一项主要视觉；新增image-chart明确支持同页图片与紧凑原生图表两项必需视觉，详见docs/图片与原生图表联合表达.md。更多必需视觉时仍拒绝省略。
- 图片/图标使用image-led、image-balanced、image-right、image-story；仍由实际文字容量选用。image-right为左文右图，主体裁切由focus及实际预览确认。
- 关系图读取relationship-fragment/1，保留原分组、节点、文字和绑定连接符。
- 图表读取chart-style-fragment/1或trend-annotation-fragment/1，保留工作簿、事实和注释。
- 常规13.333×7.5英寸宽屏、微软雅黑、同一背景角色色。预制原生图须留出标题/页脚区域，并在所选色板中制作。

封面、章节和行动结尾已接入frame-prepare，按docs/封面章节与行动结尾.md准备后进入素材包。没有实现任意模板自动适配、复杂表格或多主视觉拼贴；这些继续走专用模板/制作路线。design-system中的布局名与字体/角色色会应用到本入口支持的配方，不代表任意Office/WPS母版的几何均能被还原。source_note和小标题仍由作者写，工具不自动编事实。

## 可追溯输出

- deck-spec.json：保留原页ID、主张、正文、来源与事实。
- bindings.json：记录大纲/素材包/设计系统哈希，各页body_index对应的真实element_id、主要视觉对象和容量计划；一个正文跨两栏仍保留完整映射。
- composition.json：指向真实PPT和spec的阶段交接件。
- build/：现有规范化、原生对象检查和PPT文件。

素材包里的图片身份、字节、来源、fit和页归属保持一致；关系片段与大纲模型必须对应，图表事实必须与大纲相同。来源、许可、事实一致性与实际视觉效果各按其范围检查，不把文件存在当审美通过。

## 已验证的新题材

27号任务使用校园公共服务题材，通过本地素材检索选择相关场景，制作图右文左、同维度比较与合成图表三页。最终拼页使用本入口，而不是题材专用拼页脚本。生成场景与合成数据均有可见标注，原客户文件未改动。对新题材可重用请求结构，内容、素材与数据须重新准备，不能机械照搬样例业务文字。
