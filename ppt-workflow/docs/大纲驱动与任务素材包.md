# 大纲驱动、素材先行、模板确认后逐页制作

这是本项目新任务的默认生产顺序。新增需求文件写production_mode: outline-assets-template，并沿用quality_profile: quality-v1。旧任务没有该字段时保持兼容，不伪造历史审核或自动迁移。

## 生产顺序与审核点

1. **需求确认（ppt-intake）**：确定受众、目的、时长、页数、已有材料、品牌、目标软件与原生编辑要求。已有品牌模板优先作为约束，不为了顺序而弃用用户模板。
2. **详细大纲（ppt-outline）**：先把内容写到逐页可执行，而不是只写背景/意义等目录。提交content-outline.json、content-plan.json与production-brief.json，审核论证、正文、证据、视觉任务和资料缺口。
3. **按大纲备齐任务素材（原阶段内的准备工作）**：ppt-template按视觉任务检索比较，ppt-compose只执行下载、制图、预制与打包子任务，此时不制作整份最终PPT、不跳过阶段批准。真实图片、图标、原生图表数据/源文件与预览集中到本任务“素材”目录，保留来源和用途映射。给用户看真实候选及缺口，不能临时搜一张就立即作为成品插入。
4. **选模板与代表页（ppt-template）**：根据大纲的内容结构、文字量、素材构图及编辑要求选择或创建整套模板；用真实任务素材打封面、图表与复杂内容代表页。统一字体、角色色、版式规则及素材处理方式后，用户审核模板/样页和最终素材包。素材初筛可保留原色/中性预览；图标配色等随模板确定，变更后重打新版本素材包再提交，不能在批准后悄悄替换已绑定文件。
5. **逐页制作（ppt-compose）**：按已批准大纲的顺序，每页从任务素材包取用，落实正文、图表、图像、注释与来源；每页导图自查并记录完成/问题，再继续下一页。阶段成果交审；与预期差异大时优先检查前几页，不一路做完整套才发现方向不对。
6. **美化与独立审核（ppt-polish / ppt-review）**：先修具体视觉问题，再独立看全套和逐页效果，核对事实、素材用途、编辑性及跨页一致性。保留六个独立阶段Skill；素材准备是其中的明确子步骤，不增设混合职责的万能Skill。

用户审核须依据具体文件与真实预览记录；命令检查通过不等于用户批准。关键资料未核实或必需素材没准备好时说明缺口并返回对应准备步骤。

## 大纲必须细化的内容

content-plan已有的问题、主张、证据、推理、限制、衔接和任务检查继续使用。production-brief/1额外定义逐页可执行正文和素材需求，与content-outline的页ID、顺序和takeaway完全一致：

- body_blocks：拟实际使用的正文段落/短句，不能只是“介绍背景”等写作指令。
- speaker_notes：这一页怎样讲、重点是什么、如何承接前后；内容仍需人工核验。
- visuals：每个视觉任务有id、kind（image/icon/chart/diagram/table）、required、purpose、composition_hint、search_terms、source_refs、fact_refs。
- purpose说明这张图帮助解释什么；composition_hint描述主图/文字的关系、比例倾向、留白与主体位置，不在模板之前固定像素坐标。
- chart必须绑定已有事实；来源/事实ID必须存在。图片不能冒充客户现场记录，图标不能替代需要的主要证据。

机器检查确保字段、引用和对应关系；不能判断正文深度或论证是否充分。大纲审核仍需串读标题、检查实际正文、原资料和关键推论，不能把字段填满当作内容质量达标。

## 任务目录

```text
runs/任务名/
  大纲/
    content-outline.json
    content-plan.json
    production-brief.json
    materials-plan.json
  素材/                         # 每次打包使用新目录，如素材-v02
    manifest.json
    content-outline.json        # 内容快照
    production-brief.json
    s1/hero/
      image.png
      preparation.json
      source.svg                # 图标有
      LICENSE                   # 图标有
      download.bin              # 在线照片保留下载原件
      attribution.txt
    s2/chart/
      0-chart-request.json      # 原生图表保留数据与制作源
      1-chart-preview.png
  模板/
  制作/
  审核/
```

共享assets/online-cache用于下次复用和减少下载；本次任务素材目录用于本次生产、版本冻结与交接，两者分工不同。用户私有材料留在任务中，不自动回收进公共分发库。

## material-pack实际命令

materials-plan/1结构：

```json
{
  "version": "materials-plan/1",
  "outline": "项目内绝对路径/大纲/content-outline.json",
  "brief": "项目内绝对路径/大纲/production-brief.json",
  "items": [
    {
      "slide_id": "s1", "visual_id": "hero",
      "reason": "画面主体和留白适合本页需要，来源与主题核对完毕",
      "preparation": "项目内绝对路径/照片准备/preparation.json"
    },
    {
      "slide_id": "s2", "visual_id": "chart",
      "reason": "使用获批事实制作的原生图表，单位与注释已检查",
      "files": [
        {"role": "source", "path": "项目内绝对路径/chart-request.json"},
        {"role": "preview", "path": "项目内绝对路径/chart-preview.png"}
      ]
    }
  ]
}
```

```powershell
./.venv/Scripts/python.exe -X utf8 -m ppt_workflow material-pack --input runs/任务名/大纲/materials-plan.json --out runs/任务名/素材
```

图像项目读现有asset-prepare/asset-fetch准备件，校验实际PNG、来源与声明，复制到任务目录并重绑定preparation路径；同图跨页登记独立asset ID，避免ID/路径冲突。图表/关系/表格项目需带源文件和真实图片预览，源文件与数据是否充分仍由专业Skill查看。必需视觉任务未准备、ID不对应、图片被改动时拒绝输出，不能空文件占位。

新模式大纲指向production_brief，模板交接指向materials_pack（manifest.json），阶段系统跟踪其文件哈希。制作阶段只能在对应页使用该包的图片及来源，必需图片不能遗漏。图表/关系图的语义实现和大纲正文落实仍依靠content-plan、事实核对及独立审核，不宣称机器已经能审出所有缺项。

asset-place读取包内preparation.json，按获批布局设置区域；输出新spec后再编译或调用已验证软件适配器。原大纲的事实与证据来源冻结，素材来源允许作为新增视觉来源登记；不允许改写原来源或任意增加不关联素材的来源。

## WPS / Office执行边界

目标是让MCP承担已验证的打开、插入/修改、保存副本和实际导图操作；结构化spec保持对象映射。不是假定接上MCP就能任意操作全部软件功能或自动兼容所有会员模板。当前WPS模板副本、文字/部分原生元素能力按项目实测路线使用；原生图表转存丢工作簿仍会被门禁拒绝。PowerPoint直接PowerShell导图是已验证的备用路线，Python启动链差异未因本轮消失。

逐页制作允许由适配器自动执行和循环检查，但读大纲、选图、判断构图与审核仍由对应Skill负责。第一次代表页未经审核，不把剩余所有页面自动当作通过。


实际编译入口更新（2026-10-20）：使用`python -m ppt_workflow editorial-build --input <spec.json> --design <design-system.json> --node <node.exe> --out <全新runs目录>`。该入口保留原始包与规范化日志，并检查原生对象及包结构。底层JS输出可能含已知PptxGenJS多余母版声明，不能直接凭能导图就交付；design参数只支持已实现的布局定义，不声称重建任意外部模板。
